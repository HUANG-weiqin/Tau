# 扩展

`updated: 2026-11-18`

## 这一页管什么

本页只给扩展的核心原则、取舍顺序、推导顺序和大致方向。具体怎么接，按原则读对应的模块页推出来。这里不写方案，也不写到代码。

该不该做，按本页的[取舍顺序](#取舍顺序)定。

## 核心原则

1. **沿着运行循环长，不开旁路。** tau 只有一个形状：输入进信箱，纯函数决定，做副作用，结果作为新输入回来（[运行循环](kb-overview.md#运行循环)）。外面的事只在边上变成一条输入，比如 CLI 的请求。决策和状态不出这个循环。例外是建进程的请求（`start` 和 `fork`）：它们只建新进程，不改已有的进程，新进程之后的变化都走这个循环（[D49](kb-decisions.md#d49-fork-进内核)）。删除的请求（`prune`、`remove`、`sweep`）也是例外：它们不改任何进程的状态（进程记录和当前段）。`prune` 只删旧段，`remove` 只删空闲、没有任何地方引用的进程，`sweep` 只删没人引用的图片（[D59](kb-decisions.md#d59-删除原语旧段和空闲进程)）。写记忆的请求（`memory_write`）也是例外：记忆不是进程状态，它像 `now` 一样经 `Env` 进 `decide`，协议写入的效果和同预设的兄弟进程写入一样（[D64](kb-decisions.md#d64-内核的自由度给上层事实对称的控制和可组合的动作)）。只读的请求（`ps`、`inspect`、`check`、`history`、`memory`、`blob`、`watch`）不改任何东西，不算旁路。`backup` 也不改库里的任何东西，只在库外写一个新文件，不算旁路（[D73](kb-decisions.md#d73-backup-请求)）。`reconfigure` 不在例外里：它变成信箱里的一条输入，由 `decide` 处理，和 `send` 一样（[D71](kb-decisions.md#d71-会话配置reconfigure会话快照可改)）。
2. **先说清它是哪一种。** v2 的心智模型见[总览](kb-overview.md#认知模型)，来由见 [D47](kb-decisions.md#d47-v2-的来由六个缺口和-v1v2-的对照)。一件进来的事，是信件或新的输入种类。一件要做的事，是工具：只碰库的是库内工具（例外：`spawn` 还读预设文件，见 [D36](kb-decisions.md#d36-第-4-步第二部分进程之间的工具的执行和两处例外)），在事务里做；碰外面世界的是库外工具，由执行器做。新工具不加输入种类和阶段，结果走已有的工具结果。调用模型的参数放进快照。给上层看的是协议请求。大块数据进表，按引用存（像 `blobs`）。不加阶段：要等别的进程，就等它的回信；别的要等的事，放上层。说不清是哪一种，就还没想清楚。
3. **状态只在进程记录和工作段里。** 不在它们之外加可变字段。能算出来的不存。这是 AGENTS.md 的[状态规则](../AGENTS.md#必须遵守的规则)，扩展时最容易被绕开。
4. **先保证崩溃后正确。** 服务在任何时刻被杀，新功能都要处在说得清的状态。库外的事被打断，就报“被中断，结果未知”，不自动重做。先写崩溃和竞态的最小反例，再写代码。
5. **可换的部分只换实现。** 记忆有接口。命令只走 `bash` 一处。上层只依赖线协议、CLI、工具定义和预设。换这三样的实现不动内核。别的不预留接口。上层加工具只走工具定义：它的格式和运行是契约（[kb-tools](kb-tools.md#工具定义)）。上层的工具要原子地做已有的库内动作，就在结果里声明，不为它另加内置工具（D64）。
6. **不做假边界，不重复外部工具。** 能被 bash 绕过的限制不做。Git、编辑器、终端能完整替代的不做。
7. **模型只从三个入口知道事情。** 三个入口是：开段时的系统提示词、`decide` 写进消息的正文、工具结果（[认知模型](kb-overview.md#模型知道事情的三个入口)）。要让模型知道新东西，就选其中一个。不开第四个入口，不改写已有的消息。例外：请求里的旧图成批省略，库不变（[D40](kb-decisions.md#d40-第-6-步前一半的选择)）。段里消息的 `tau` 字段不发给模型，不算入口。
8. **给上层自由度。** 内核对上层的形状有四类（[D64](kb-decisions.md#d64-内核的自由度给上层事实对称的控制和可组合的动作)）：
   1. 事实可读：持久事实就是这五样，上层都经协议原样读到：进程记录用 `inspect`；段用 `history`，消息带 `tau` 结构；记忆用 `memory`；图片用 `blob`；预设读成的快照和限度用 `check`。信箱的行和 `effects` 表是处理中的中间状态，每次 `pump` 都排空或开始，不算。投影只是给模型和人的摘要。
   2. 控制对称：模型能对进程做的控制，外面也能做：寄信（`send`，可带 `from`、`reply`）、换段（`send` 带 `handoff`）、停止、建进程（`start`、`fork`，可带 `id`）、读写记忆（`memory_write`）。D71 又加了改会话的配置（`reconfigure`）：改这个会话的快照而 ID 不变，调用参数立即生效，结构性字段换段时生效。
   3. 动作可组合：已有的库内动作（`post`、`spawn`、`stop_process`、记忆工具），工具定义能在结果里声明，和工具结果在同一个事务里执行。`handoff` 和 `self` 不能声明：换段由 `decide` 看段里的调用发起，`self` 的结果脚本从协议就能读到。
   4. 参数可传：调用模型的参数，预设用 `options` 写。
   - 这四类由 D64 一次补齐，D64 的原语不要求本机用过。
   - 以后内核因为别的功能加一样事实或控制，同时给上层，上层那一份不另要用量：记录加字段，`inspect` 自动读到；加库内动作，就列进能声明的库内动作。
   - 判一个新功能时，D64 的原语当成已有的原语用：判第 3、4 条时上层能用它们。这不算第 2 条的“已有别的机制”。功能要用到四类里 D64 还没给的东西，算这个功能的一份代价，照[取舍顺序](#取舍顺序)判，第 2 条照样在第 4 条之前。
   - D64 列了加完以后还只能改内核的类别，那只是已知的线索，不是门槛。判功能照取舍顺序走完。

## 取舍顺序

一个功能放在内核还是上层，按这一节定。设计稿第 2 节只留链接。

**上层能完整接管、不付出代价的功能，内核不做。**

代价是下面任何一种：

1. 不原子：崩溃后可能重复做、漏做，或者说不清做没做。例如工具定义里运行 `tau send` 寄信：寄出以后、写结果之前崩溃，模型看到“被中断”再寄一次，信就重复（[kb-contract 的原语表](kb-contract.md#原语和它在内核的理由)）。
2. 丢数据：上层没在运行时，事情就漏了。
3. 看不见：模型或人该知道的事，没有地方知道。
4. 慢：明显变慢，或者随年头越来越慢。
5. 做不到：上层没有办法做到。

一个功能放在哪，按这个顺序定。第一条成立的就是答案：

1. **做法本身就违反下面几条之一，放在内核还是上层都一样**：不做能被 bash 绕过的假边界；不写兼容代码；项目目录里不写任何东西（以上是 AGENTS.md 的规则）；沿着运行循环长，不开旁路（原则 1）。原则上不做，写成新的决策条目，按 [D46](kb-decisions.md#d46-v2-也不做的) 第三张表的列来写，并链接 D46。
   - AGENTS.md 的别的规则不按这一条判断。YAGNI 和“外部工具能完整替代”按第 2 条。和[不变量](kb-contract.md#不变量)相同的，按第 4 条第 1 支。
   - 假边界按全部进程看。一条规矩要所有进程都守才成立的（例如进程之间的文件锁），只要还有一个进程有 bash，就是假边界。预设不给 bash，只管得住这个预设自己的进程：[D46](kb-decisions.md#d46-v2-也不做的) 第三张表的“在预设里决定给不给 bash”说的是这一种。所以这类功能的“要的话怎么办”只写缩小范围的做法，不写成能硬挡：别的预设的进程有 bash，照样绕得过。
   - “做法本身”指这个功能怎么做都违反。有一种做法能沿运行循环做（外面的事变成一种输入，交给 `decide`），就不归这一条，往下判。那种做法要推翻不变量的，按第 4 条第 1 支，排在第 2 条之后。
2. **本机的 Pi Web 没用过，或者 tau 不需要**：现在不做，也不进内核。写成新的决策条目，按 [D46](kb-decisions.md#d46-v2-也不做的) 第一张表的列来写，并链接 D46，写明要的话上层怎么做。上层做不到的，写明做不到，用上了再按取舍顺序重判。
   - 真实用过是功能进内核的必要条件，不是充分条件。D64 补齐四类自由度的原语不按这一条（原则 8）。
   - tau 不需要，指三种情形之一：它要满足的需要，tau 已有别的机制满足；外部工具能完整替代；用它的那个功能，tau 不做。要写明是哪个机制、哪个工具或哪个功能。
   - 两种理由是“或”：用过只说明前一种不成立，还要看 tau 需不需要。照用已有的工具、请求或命令就满足的，是“已有别的机制”，按这一条，例如在一条回复里多次调用一个已有的工具。“满足”拿功能写明的要求来比：做不到其中一条（例如只能晚一些、粗一些做到），或者要上层另做东西补上的，都不算“已有别的机制”。记录的第三列写照用哪个机制，上层不另做东西。第 3 条的“上层做”，指上层另做的东西：工具定义、上层的程序、上层显示用的约定。D64 的原语让上层能做到，不等于“已有别的机制”：要界面或上层程序另做东西去调它的，是第 3 条的“上层做”；第 2 条只另看本机用没用过。[kb-extras](kb-extras.md#pi-web-的功能在-v2-上的做法) 表里归类不是“已有”的行，也都是上层另做的东西，不算已有别的机制。两种理由都写时，每一种都要单独成立；“已有别的机制”要逐条对照功能写明的要求，例如功能写“由 tau 挑”，要模型自己列、自己挑的，就不满足。
3. **上层做不比内核版多付代价**：放上层（[kb-extras](kb-extras.md)）。内核版也要付的代价，不算上层的代价。例如库外工具崩溃时报“被中断”，内置的 bash 也这样。
   - 预设要改用上层的东西（例如不给内置的 `bash`，改给一个工具定义），不算代价，也不算做不到：预设本来就由用户写。
   - 五种代价逐一说明不多付，包括上层没在运行时丢不丢东西。
4. **上层做要付代价（包括做不到）**：按下面三支的顺序判断，第一支成立的就是答案。
   1. 内核版要推翻[不变量](kb-contract.md#不变量)：不进内核。上层能做一部分的（可以有代价），写进 [kb-extras](kb-extras.md#pi-web-的功能在-v2-上的做法)；上层一点都做不了的，写成新的决策条目，按 [D46](kb-decisions.md#d46-v2-也不做的) 第二张表的列来写，并链接 D46。两处都写明推翻哪一条、上层的代价。
   2. 代价只出在本机没用过的部分，或者只在崩溃时出现、重做无害：按 YAGNI 接受，放上层。[kb-extras](kb-extras.md#pi-web-的功能在-v2-上的做法)写明按这一支。
      - “没用过的部分”指出这份代价的那种情形，不是整个功能。功能用过，但出代价的那种情形本机没出现过，也算。例如扇出上限：触发过 4 次，代价只在失控时出现，本机没出现过失控（kb-extras）。
   3. 其余的：进内核。

怎样用这个顺序：

- 第 1、2 条按整个功能判断。第 3、4 条按上层的每一份代价分别判断。功能有几部分的，上层不多付代价的部分归第 3 条。各部分落在不同的条，归类分开写，例如“4.1（X 那份）；Y 那份 3”。
- 归类只说这个功能自己。它用到的已有原语有自己的归类（例如 `fork` 是 4.3），不算到这个功能头上。按第 1、2 条定的功能，归类就是那一条。
- 这个顺序判的是功能。D64 的原语不经它判，判功能时当成已有的原语。判第 3、4 条时，先看上层用 D64 的原语能不能去掉这份代价；能去掉，就不算代价。用到四类里 D64 还没给的东西，算一份代价，照常判（原则 8）。
- 写成新的决策条目的（第 1、2 条，第 4 条第 1 支里上层一点都做不了的），只写这一条：不改 D46 的表，也不往 kb-extras 和本页的方向表加行。要的话怎么做，写在这一条里。
- 内核版，指去掉上层这份代价、改动最少的内核做法。
- 落到第 4 条第 3 支的那几份代价，内核为它们加对应的原语。功能本身照样放上层。

## 推导顺序

加功能时按顺序回答下面的问题。每个问题的答案都要能落到右边那页的规则上。全部答完，接在哪里也就定了。

| # | 问题 | 怎么答 | 依据 |
|---|---|---|---|
| 1 | 该不该做？ | 按[取舍顺序](#取舍顺序)定，答出按哪一条、放在哪里。不进内核的，写明上层怎么做，答到这里为止。只有进内核的，才往下答第 2 到 8 步。在“MVP 不做”清单里的，先改设计稿。看起来合理的机制，先查 Pi Web 的教训 | [取舍顺序](#取舍顺序)、[准入规则](../AGENTS.md#准入规则)、[MVP 不做](../docs/design/mvp.md#mvp-不做)、[Pi Web 的教训](kb-piweb-lessons.md) |
| 2 | 它是哪一种？ | 进来的事是信件或新的输入种类。要做的事是工具：只碰库的是库内工具（例外：`spawn`，见 [D36](kb-decisions.md#d36-第-4-步第二部分进程之间的工具的执行和两处例外)），碰外面的是库外工具。调用模型的参数放进快照。给上层看的是协议请求。大块数据进表，按引用存（像 `blobs`）。能从已有状态算出来的，是派生值或投影的字段，不是新状态。不加阶段：要等别的进程，就等它的回信；别的要等的事，放上层。外面的事件由服务在边上变成输入 | 原则 1、2，[认知模型](kb-overview.md#进程是一个小状态机) |
| 3 | 状态放在哪？ | 只在某个阶段有意义的数据，放进那个阶段。属于对话的，进工作段。跨段要用的，进进程记录。Agent 的长期知识进记忆，只走记忆接口。能算出来的不存 | 原则 3，[kb-kernel 的状态](kb-kernel.md#状态)、[kb-memory](kb-memory.md) |
| 4 | 在哪个事务里改？ | 一条输入一个事务，事务里做什么只写在 kb-store。库内工具在这个事务里同步执行，不 `await`。库外的进待办副作用表 | [处理一条输入](kb-store.md#处理一条输入) |
| 5 | 服务在任何一步被杀，状态是什么样？ | 列出每两个提交之间被杀的情形。库里的必须说得清。库外的被打断，就报“被中断”，不自动重做。先写最小反例测试 | 原则 4，[崩溃窗口](kb-executor.md#崩溃窗口) |
| 6 | 模型怎样知道？ | 整段都成立的，进系统提示词。发生过一次的，由 `decide` 写进下一条消息。需要时才看的，做成工具结果 | 原则 7 |
| 7 | 用户和 Agent 怎样看到？ | 加进投影，`self` 和协议的 `ps` 看同一份；`tau ps` 冻结在 v1 的字段，人用上层的命令行看新字段。流式文本不进库 | [投影与命令](kb-kernel.md#投影与命令) |
| 8 | 怎么证明它对？ | 纯函数写单元测试。顺序和崩溃写随机序列和崩溃注入测试。过完成门槛 | [完成门槛](../AGENTS.md#完成门槛) |

答完回头核对一遍。答案违反 AGENTS.md [必须遵守的规则](../AGENTS.md#必须遵守的规则)的任何一条，就换一种做法。确实要破例，先在[决策记录](kb-decisions.md)写清理由。

## 大致方向

下表写大致方向，细节见各行链接的页。

| 想加的 | 方向 | 已有线索 |
|---|---|---|
| 定时器、自我唤醒 | 内核不做。上层用系统计划任务到点运行 `tau send`。代价：`ps` 看不到预约，服务没在运行时这封信会漏。见 [D46](kb-decisions.md#d46-v2-也不做的) 第一张表 | [D14](kb-decisions.md#d14-yagni-审查移出-mvp-的-20-项) |
| Agent 的控制命令 | 内核加库内工具：`handoff` 换段，`stop_process` 停进程，`post` 寄信。见 [kb-kernel](kb-kernel.md#主动换段handoff)和 [kb-store](kb-store.md#进程之间的工具) | [D9](kb-decisions.md#d9-自省同一份投影) |
| 推送状态行 | 不做，用 `self`。见 [D46](kb-decisions.md#d46-v2-也不做的) 第一张表 | [D25](kb-decisions.md#d25-上一轮没有正常结束时下一条消息加说明) |
| Agent 派生、进程之间发消息 | 库内工具 `spawn`、`post`、`stop_process` 和回信。要等子进程，就等它的回信，不做“等待”状态机。见 [kb-store](kb-store.md#进程之间的工具)、[kb-kernel](kb-kernel.md#回信) | [Pi Web 的教训](kb-piweb-lessons.md) |
| 审批 | 不做。审批当安全边界会被 bash 绕过。Agent 在回复里先问，再等下一封信。见 [D46](kb-decisions.md#d46-v2-也不做的) 第三张表 | 无 |
| 新工具、MCP | 先问能不能写成工具定义。MCP 由上层的中转进程为每个 MCP 工具生成工具定义。见 [kb-extras](kb-extras.md#pi-web-的功能在-v2-上的做法)的 MCP 一行 | [Pi Web 的教训](kb-piweb-lessons.md) |
| 换段阈值、上下文大小 | 不做新功能：预设的可选字段 `handoff`（token 数）把换段阈值调低，只能调低，不能调高。见 [kb-kernel 的换段阈值](kb-kernel.md#换段阈值)和 [D51](kb-decisions.md#d51-预设加-handoff换段阈值只能调低)。运行中按会话改用 `reconfigure`，立即生效，不换 ID（[D71](kb-decisions.md#d71-会话配置reconfigure会话快照可改)）；换成另一个预设 ID 才用 `fork` 带另一个预设 | [D22](kb-decisions.md#d22-换段阈值用量估算和记忆上限) |
| 日志、整理 | 换记忆的实现。整理由一个进程来做，定时用上层的计划任务。见 [D46](kb-decisions.md#d46-v2-也不做的) 第一张表 | [D6](kb-decisions.md#d6-mvp-的记忆是带版本号的键值存储)、[D14](kb-decisions.md#d14-yagni-审查移出-mvp-的-20-项) |
| 挂载 | 不只是换实现，要改预设和记忆接口。先改 D6 | [D6](kb-decisions.md#d6-mvp-的记忆是带版本号的键值存储) |
| 沙箱 | 上层用在沙箱里运行命令的工具定义做，预设不给内置的 `bash`。只换 `bash` 的实现要按改契约做。见 [D46](kb-decisions.md#d46-v2-也不做的) 第一张表 | [D7](kb-decisions.md#d7-第一版不做沙箱) |
| Web UI | 放上层：HTTP 桥走线协议，读投影，要详情时读 `inspect`。见 [kb-extras](kb-extras.md) | [D9](kb-decisions.md#d9-自省同一份投影)、[D16](kb-decisions.md#d16-服务只在命名管道上监听mvp-用-cli) |
| 上层要读内核的某样事实、做模型能做的某个控制、包住库内工具、设调用模型的参数 | 先按取舍顺序第 1、2 条判该不该做。要做时用原则 8 的原语：上层不多付代价就是第 3 条；还有代价的按第 4 条判。D64 的“还只能改内核的类别”是线索 | [D64](kb-decisions.md#d64-内核的自由度给上层事实对称的控制和可组合的动作) |
| 花费统计和上限 | 统计用投影里的累计用量。上限放上层，用累计用量、`watch` 和 `stop` 尽力而为。见 [D46](kb-decisions.md#d46-v2-也不做的) 第一张表 | 原则 3 |
| 服务重启后接着做被打断的一轮 | 不做新功能：崩溃后正在运行的库外动作作为“被中断”送回，被中断的那一轮以“出错：服务重启，……被中断”结束，不自动重做（[不变量 5](kb-contract.md#不变量)、[kb-executor 的崩溃窗口](kb-executor.md#崩溃窗口)）。要接着做，由上层在重启后给这类进程寄一封“继续”，和任务清单的续跑同一套做法，代价也一样：回信已经带着出错寄出，上层没在运行时不续跑（[kb-extras](kb-extras.md#pi-web-的功能在-v2-上的做法)）。本机 Pi Web 的热重载后续跑 21 条 | [D54](kb-decisions.md#d54-使用数据重核) |
| fork、从某条消息重来 | 内核的 `fork` 请求：复制当前段的前缀，新进程不带父进程和用量。上层用不了 `history` 加 `start`，第一封信最多 32 KiB。可选的 `preset` 参数带着完整当前段换角色（新进程的 ID 变了，那份代价仍在上层，见 [kb-extras](kb-extras.md#pi-web-的功能在-v2-上的做法)）。见 [kb-kernel 的 fork](kb-kernel.md#fork)、[D49](kb-decisions.md#d49-fork-进内核)和 [D52](kb-decisions.md#d52-fork-带-preset给进程换角色)；命令行在上层的 `tx` | [D46](kb-decisions.md#d46-v2-也不做的) |
| 删旧数据、清理 | 内核只给 `prune`、`remove`、`sweep` 三个原语，删什么、什么时候删由上层定。见 [D59](kb-decisions.md#d59-删除原语旧段和空闲进程) | [kb-piweb-lessons](kb-piweb-lessons.md#一个文件混装三种寿命) |
| 图片、截图等大块数据 | 存进库的 `blobs` 表，和引用在同一个事务里。见 [kb-store](kb-store.md#图片) | [Pi Web 的教训](kb-piweb-lessons.md) |
