# 决策记录

`updated: 2026-11-17`

## 这个模块是干什么的

记录跨模块的决定：决定了什么、为什么、放弃了什么。模块内部的决定写在各模块页里。

每条都标明状态：

- **已确认**：用户明确同意或亲自提出。
- **默认**：我提出的默认值，用户还没确认。改它不需要推翻别的决定。

新增依赖也记在这里，写明理由。

后面的决策可以修改前面的决策。被改掉的说法在前面的条目里直接改正，后面的条目记录为什么改。

## 决策

### D1 从头重写，不在 Pi Web 上重构

- 状态：已确认。
- 理由：Pi Web 的状态散在二十多个容器里，测试按现有结构写成；不删减功能，状态机只会变得更诚实，不会变小。证据见 [Pi Web 的教训](kb-piweb-lessons.md)。
- 放弃：逐步收拢 Pi Web 的 Actor 阶段标志。

### D2 运行时只有预设和进程

- 状态：已确认。用户提出“全局助手 / 项目多 Agent / 临时 Agent”三种划分，以及“记忆是资源，记忆加 Agent 等于干活的会话”。
- 决定：Agent 不是运行时对象，只是预设的 ID。用户说的三种 Agent 是写预设的三种方式，不是类型；代码里没有“全局助手”或“项目”的概念。
- 放弃：
  - 每个 Agent 一个常驻对象：并行时归属不清。
  - “资源也是进程”（所有东西都是带信箱的单元）：统一接口会掩盖资源之间的差异，而且工作区并不归宿主所有。只有进程有信箱。

### D3 同一个 Agent 的进程可以并行

- 状态：已确认。用户的理由：并行进程只共享记忆，只有写记忆时需要处理冲突。
- 放弃：常驻 Agent 一次只做一件事。

### D4 纯 decide、单信箱、事务提交

- 状态：已确认。用户的目标是“状态统一管理，其余都是纯函数”。
- 决定：纯函数 `decide` 处理每条输入；进程在等的副作用由纯函数 `effectOf` 算出；所有输入进同一个信箱；一条输入一个事务。签名见 [kb-kernel](kb-kernel.md#函数)。
- 放弃：
  - 一个全局 store 加异步 reducer：每次跨越 `await` 都要复核状态，这正是 Pi Web 复杂的来源。
  - 照字面理解“全部纯函数”：SDK 流、子进程和崩溃窗口永远不纯。它们被关进执行器，执行器不做决策。

### D5 换段取代压缩

- 状态：已确认。
- 决定：上下文到阈值时，进程写交接说明，然后开新段。新段由“预设 + 记忆视图 + 交接说明”组成。（D22：写说明时还没处理的用户消息也原样带到新段。）
- 放弃：Pi 原生压缩；Pi Web 的 `reset_context`，它保留全部原始用户输入，超过 128 KiB 就拒绝，所以长会话下会失效。

### D6 MVP 的记忆是带版本号的键值存储

- 状态：已确认。用户以后会自己设计更抽象、解耦的分层记忆。
- 决定：记忆模块对外只暴露窄接口（视图、读、写、删）。写入带版本号，版本对不上就失败并返回最新值。预设的 `tools` 含 `memory` 时进程才有记忆库，库 ID 等于预设 ID。接口带 `ns` 参数，因为一张表里存着多个库。
- 长期方向（都不在 MVP 里）：
  - **挂载**：进程可以挂载多个记忆库，每个挂载有“只读或可写”和“进视图或按需读取”两个属性；运行中可以临时挂载；库有标题和简介。
  - **日志加整理**：并行进程只追加日志，由整理进程写长期笔记；笔记只降级，不自动删除。
- 放弃：
  - 记忆库的“主人”：谁能写由挂载决定，再加主人就是同一个事实的第二个来源。
  - “私密”标记：叠在挂载上的信息流策略，由用户在预设里决定挂不挂即可。

### D7 第一版不做沙箱

- 状态：已确认。用户担心沙箱会让项目变复杂。
- 决定：所有命令只走 `bash` 这一个副作用。以后加沙箱：上层用在沙箱里运行命令的工具定义做，预设不给内置的 `bash`；只换 `bash` 的实现要按改契约做（D29 改正了之前“以后加沙箱只换这一处”的说法）。原则是：不拦，但能发现（git、版本检查），能撤销。
- 已知风险：一个有 bash 的进程如果被说服，可以删除项目外的文件、读取密钥、联网发送数据。这和 Claude Code 默认模式的风险相同。
- 补充：工具列表是“爆炸半径”，不是安全边界。模型能被说服（困惑的代理人问题），沙箱也解决不了这一点。

### D8 一个用户级 SQLite

- 状态：已确认。
- 决定：预设和工具定义（都是 `~/.tau/` 下的文件）以外的全部数据放在一个用户级库 `~/.tau/tau.db`，包括图片（`blobs` 表），项目目录里不写任何东西。表、WAL 设置和备份办法见 [kb-store](kb-store.md#位置)。
- MVP 不做迁移：有了需要保留的真数据再加。
- 放弃：
  - “库可以丢，纯文本才是真相”：这个前提是笔记为纯文本文件；记忆改成键值存储后不再成立。
  - 按项目存数据（像 `.piweb/`）：跨会话消息需要多文件原子流程；`git clean -fdx` 会删掉被忽略的目录。

### D9 自省：同一份投影

- 状态：需求已确认（用户希望 Agent 能像用户一样看到 harness，包括上下文剩余、时间等）。
- 决定：`observe` 同时供 CLI 和 Agent 的 `self` 工具使用。`self` 只读，这是接口的范围，不是权限边界：有 bash 的进程可以直接运行 `tau` 命令（D18 改正了之前“Agent 只能看，不能控”的说法）。
- 以后给 Agent 加控制命令时，命令进同一个信箱。

### D10 模型层只用 pi-ai，循环和工具自己写

- 状态：已确认。
- 已核实（`@earendil-works/pi-ai` 1.0.0）：
  - 模型目录带 `getModel` 和 `streamSimple(model, context, options)`。`streamSimple` 要整个模型对象，所以调用时仍从目录取模型。
  - 内置的模型目录是 `@earendil-works/pi-ai/providers/all` 的 `builtinModels()`。`createModels()` 返回空目录，没有任何 provider；测试用它装 faux provider。（D20 改正了之前“`createModels()` 就是模型目录”的说法。）
  - 转换消息时，连续的用户消息原样传过。各家模型接不接受，第 3 步用真模型核实。（后来只在 opencode-go/deepseek-v4.1-flash 上核实，见 [D24](#d24-真模型验收)。）
  - `~/.pi/agent/auth.json` 的凭据和 pi-ai 的 `Credential` 同形（`api_key` 或 `oauth`）。tau 还不读它。（D23 改为只读复用其中的 `api_key` 条目。）
  - `providers/faux` 提供假模型，可以用于测试。
  - 用户消息带 `timestamp`；助手消息带 `usage`（含 `totalTokens` 和 `cost`）、`stopReason`（`pending`、`stop`、`length`、`toolUse`、`error`、`aborted`、`deferred`）和可选的 `errorMessage`。模型失败写在助手消息里，不抛出。
  - pi-ai 自己估算用量时取 `totalTokens`，为 0 时取 `input + output + cacheRead + cacheWrite`。
  - 模型带 `contextWindow`；请求上下文由 `systemPrompt`、`messages` 和可选的 `tools` 组成。
  - 转换消息时，pi-ai 给没有结果的工具调用补一条结果，跳过 `error` 和 `aborted` 的助手消息；接口要求工具结果后面接助手消息时，自动插入一条。（后来核实：只在 openai-completions 里有，要模型的 compat 打开 `requiresAssistantAfterToolResult`，内置模型都没打开，见 [D24](#d24-真模型验收)。）
- `contextWindow` 在进程启动时冻结进快照，是为了让 `decide` 不做 I/O。
- 理由：Pi Web 最复杂的代码都源于 Agent 循环不归自己，只能适配 SDK 的私有 API。
- 放弃：`@earendil-works/pi-coding-agent`（143 MB，带扩展、codemode、TUI）。4 个工具自己写。

### D11 SQLite 驱动

- 状态：已确认（随 D18）。
- 已核实：`node:sqlite` 在 Node 24.14 上会打印 `ExperimentalWarning`；运行时加 `--disable-warning=ExperimentalWarning` 后不再打印。
- 后来：Node 24.15 删掉了 `node:sqlite` 的实验警告，同时把它标为 release candidate（PR #61262）。24.22.1 上核实过，不加参数也不打印。最低版本 24.21（[D15](#d15-工具链没有构建步骤)）晚于 24.15，所以删掉了这个参数。24.21 本身没有运行过。
- 决定：用内置的 `node:sqlite`，只用最基本的同步 API。少一个原生依赖，也不用为 Node 升级重新编译。
- 代价：它还不是稳定 API，几年内可能变化。变化时要改 `store/`、`memory/kv.ts`，以及执行器和服务里直接写的 SQL（D20 改正了之前“只改 `store/`”的说法）。
- 放弃：`better-sqlite3`。它成熟，但是要编译原生模块。

- 规矩写在 AGENTS.md 的“准入规则”和“小而硬规矩”里。

### D13 名字叫 tau

- 状态：已确认。
- 含义：τ = 2π，Pi 的下一代；《τ 宣言》主张用 τ 取代 π；在物理里，τ 是衰减的时间常数，对应“遗忘”。

### D14 YAGNI 审查：移出 MVP 的 20 项

- 状态：已确认（2026-11-15）。
- 移出的内容列在设计稿的 [MVP 不做](../docs/design/mvp.md#mvp-不做)。几条主要理由：
  - **日志**：MVP 不删旧工作段，原始对话本来就在库里，日志是重复数据。
  - **定时器**：它在长期设计里的唯一用途是记忆整理，而整理不在 MVP 里。
  - **Agent 派生 Agent**：用户要的是“不带记忆的临时 Agent”，不是“Agent 能派生 Agent”。临时 Agent 就是不带记忆的预设。（D28 改正了之前的说法：v2 做了 `spawn`。）
  - **插话**：运行中的消息排队到本轮结束，少了一组插入位置的规则和测试。（D28 改正了之前的说法：v2 做了，规则是安全点投递，很短。）
  - **路径限制、权利对象**：有 bash 就能绕过，是假边界。改为预设里的工具列表。
  - **`cancelling`、`paused`、`closed` 阶段**：停止时直接补“已中止”的结果并回到 `idle`，迟到的结果按 ID 丢弃。
  - **花费上限、并发上限、全局停止**：每一轮都由用户发起，“每轮步数上限”加上用户本人就能约束。（D28 改正了之前的说法：v2 有派生，每一轮都由用户发起不再成立，并发上限和扇出上限的风险在 D29 接受。）
- 结果：阶段 7 种减到 4 种，输入 6 种减到 3 种，emits 6 种减到 3 种，表 11 张减到 6 张，依赖从至少 6 个减到 3 个。
- 后来的修改：D17 把阶段减到 3 种、表减到 5 张，并把副作用结果按种类分成模型结果和工具结果，输入变成 4 种；D18 删掉 emits（副作用由 `effectOf` 算出），并把“停止时补‘已中止’”改为 `endTurn` 的两种补法。

### D15 工具链：没有构建步骤

- 状态：已确认（随 D14）。
- 已核实：Node 24.14 直接运行 `.ts` 不打印警告；`node --test` 自动找到 `*.test.ts`。（后来核实：24.22.1 上同样成立。）
- 后来改为要求 Node 不低于 24.21：测试清理靠 `rmSync` 的重试，24.21 之前它在 Windows 上不重试（[kb-tools](kb-tools.md#坑点)）。
- 决定：不用 vitest、ESLint 和 tsc 构建。测试用 `node:test`；kernel 无 I/O 用一个扫描 import 的测试检查；`typescript` 只跑 `tsc --noEmit`。开发依赖还有 `@types/node`，因为 `tsc` 要检查 `node:` 模块的类型。
- tsconfig 开 `verbatimModuleSyntax`：只有类型的 import 必须写成 `import type`，Node 擦除类型后才不会去加载它。
- 代价：只能用可擦除的 TS 语法；import 必须写 `.ts` 扩展名。
- 第 0 步定下（默认）：
  - 精确锁定 `typescript` 7.0.2 和 `@types/node` 24.19.2。
  - 测试放在 `test/`，不放在 `src/`。这样 `src/kernel/` 的扫描没有例外，`loc` 直接统计整个 `src/`。
  - import 扫描测试（`test/kernel-imports.test.ts`）同时禁止 kernel 用 `await`、`Date`、`Math.random`、`process.`、`globalThis`、定时器、动态 import 和 `require`，对应 AGENTS.md 的纯函数规则。

### D16 服务只在命名管道上监听，MVP 用 CLI

- 状态：已确认（随 D14）。D18 把协议从 HTTP 加 SSE 改为 JSON 行。
- 理由：浏览器连不上命名管道，所以不需要 Origin 和 Host 检查，也不占用端口。Web UI 移出 MVP。
- 协议：每个连接一行 JSON 请求，服务回若干行 JSON。客户端是 CLI，以及用协议的上层程序，都不需要 HTTP 的路由、状态码和 SSE 分帧。（原文“CLI 是唯一的客户端”，随 v2 的 `history` 和 `watch` 改正，见 D39。）
- 已核实：HTTP 加 SSE 在 Windows 命名管道上也能工作。以后要加 Web UI 时可以再用。
- MVP 只支持 Windows：命名管道路径、`taskkill /T /F` 都按 Windows 写。

### D17 纯度审查：同一个事实只有一个来源

- 状态：已确认（2026-11-15）。
- 决定：
  - **三种 Agent 是用法，不是类型**；预设的 `memory` 字段并入 `tools`，预设从 5 个字段减到 4 个。
  - **进程的状态 = 进程记录 + 当前工作段**。`decide` 同时看到两者；上下文用量、本段开始时间、待执行的工具调用都由纯函数从消息算出，不再存进进程记录。
  - **删掉 `segments` 表**：它的 `id`、`seq`、`opened_at` 和进程记录重复，`handoff` 又是新段的第一条消息，`closed_at` 可以从下一段推出。表从 6 张减到 5 张。
  - **记忆视图存进 `Process.segment.memoryView`**：它是开段那一刻的快照，以后算不出来，所以是正当状态。之前的设计稿没写它存在哪里。`decide` 从环境参数拿到当前视图，只在开段时使用。
  - **`failed` 并入 `idle`**：两者行为相同。上一轮的结束原因是 `idle` 的字段。阶段从 4 种减到 3 种。
  - **输入不带 ID 和时间**：事务保证恰好一次，时间由环境传入。信箱只留一个自增序号。
  - **删掉记忆的 `updated_at`、`updated_by`**，以及接口里的 `by` 参数：没有人读。
  - **命名管道就是锁**：同一个管道不能被监听两次，删掉锁文件。
  - **副作用结果按种类分型**，不用 `unknown`。
  - 按 YAGNI 删掉花费统计和“距你上次说话多久”：它们是我加的，用户没要求过。（D28 改正了之前“删掉花费统计”的说法：v2 加累计用量，只累计 token，不算钱。）
- 已核实：第二次监听同一个命名管道会得到 `EADDRINUSE`，同一个进程里和跨进程都一样（`test/server/listen.test.ts`）。

### D18 第三轮审查：两个审查者，24 项修改

- 状态：已确认（2026-11-15）。用户要求“带两个 Opus 继续提纯”，两个审查者独立审查，合并后共 24 项。
- 改正的错误（会导致状态错或死循环）：
  1. **停止和取消的竞态**：执行器可能在停止之后才开始一个副作用。改为待办副作用表由 `effectOf` 同步，停止和删行在同一个事务里。删掉 `Effect.cancel`、`effect_json` 和副作用 ID 里的进程 ID。
  2. **换段可能无限循环**：交接调用不计步，换段失败后会一直重试。改为每次调用模型都计一步，统一走 `continueTurn`；交接说明作为新段第一条用户消息；段里没有助手消息时按字节估算用量。
  3. **两个失败来源**：模型失败既可能是单独的输入，也可能写在助手消息里。改为只按 `stopReason` 处理；`length` 当作错误，因为截断的工具参数可能不完整。
  4. **记忆版本号的 ABA**：删掉再重建一个键后，旧版本号可能又对得上。改为全库自增 ID，写入 = 删旧行插新行。
  5. **`queued` 放错了层**：改为放进运行中阶段的 `Turn`。`endTurn` 给没有结果的工具调用补结果：正在等的写“被中断，结果未知”，其余写“未执行”；排队的消息合并成一条用户消息。
  6. **bash 的孙进程**：超时或中止时结束整棵进程树。（D21：代码尽力结束，有几种进程会漏掉。）
  7. **回执之前断开**：CLI 提示“结果未知”，不自动重试。
- 补上的隐藏依赖：
  8. 消息不交替（工具结果后接用户消息、连续用户消息）列为风险，第 3 步核实。
  9. `contextWindow` 在启动时冻结进快照；工具描述是 kernel 里的纯数据。（工具定义的名称、说明和参数来自快照里冻结的文件。）
  10. 删掉 `openSegment` 这类 emit：`decide` 不发出副作用。（v2 第 4 步改正：它还返回回信 `out`，由存储层在同一个事务里投递，见 D35。回信是信，不是副作用。）
  11. `start` 只建一个 `idle` 进程，第一条消息走信箱。
  12. 时区由 `Env.utcOffsetMinutes` 传入，`decide` 不读系统时区（D19 又删掉了它：本地时间改在内核外格式化）。
- 改正的假边界和多余的东西：
  13. “Agent 只能看，不能控”是假边界：有 bash 就能运行 `tau`。改为“`self` 只读是接口的范围，不是权限边界”。
  14. 工具链：加 `@types/node` 和 `verbatimModuleSyntax`；SQLite 改用 `node:sqlite`（D11）。
  15. 删掉 `self` 里的记忆统计。
  16. 兄弟进程只列不处于 `idle` 的。
  17. 协议从 HTTP 加 SSE 改为 JSON 行（D16）。
  18. 删掉 `tau chat`：连续使用 `tau send` 就是对话。
  19. 删掉 `tau backup`：停掉服务后复制 `~/.tau/`。
  20. 记忆只有一个总上限：整个库不超过视图预算，所以视图永远是全部内容，不需要截断规则。
  21. MVP 只支持 Windows。

### D19 第四轮审查：Fable 5.2 复审 D18 之后的文档

- 状态：已确认（2026-11-15）。用户要求“全部照改”。
- 改正的错误（会导致副作用执行两次、进程永久卡住或 ABA）：
  - **同步规则只看编号变化**：之前写成“新阶段在等的就插入或执行”。副作用的结果还在信箱里排队时，先处理一条用户消息，同一个副作用会被再插入或再执行一次。
  - **执行器的事务边界写死**：取行、算内容、标记 `running` 在一个事务；提交后立即登记中止开关，中间不让出；删行和放结果在一个事务；启动恢复的删行和放 `interrupted` 也在一个事务。否则崩溃会让行和结果一起消失，进程永远在等。
  - **`AUTOINCREMENT`**：SQLite 普通的整数主键会复用被删掉的最大编号，ABA 会回来。
  - **每个工具结果写入后都检查阈值**：到了阈值，给剩下的工具调用补“未执行”，然后换段。之前要等一条消息里的工具全部跑完，一次读很多大文件就会超过窗口，进程从此不能用。
  - **上下文用量写明取 `totalTokens`**，为 0 时取四项之和。开了提示缓存后，`input` 只是没命中缓存的部分。
  - **边角**：`toolUse` 但没有工具调用按 `stop` 处理；`errorMessage` 缺省时用 `stopReason`；不认识的工具在事务里直接回错误结果。

- 文档：`decide` 签名、库里有哪几张表、事务做哪几件事，只留在一处（当时是设计稿；第 2 步之后是 [kb-kernel](kb-kernel.md) 和 [kb-store](kb-store.md)）；“打开进程”改为“处理一条输入”；模块依赖改正（`store` 通过接口使用记忆）；`tau send` 挪到清单第 3 步；第 2 步用假的库内工具测试；清单的不变量改为运行中也成立的写法。

### D22 换段阈值、用量估算和记忆上限

- 状态：默认（2026-11-15）。用户还没逐条确认。从三个方案、两个评审里选出，再经一轮对抗式核查。第 6 步就地改正两处（D40）：快照还冻结 `input`；窗口够不够改为启动检查。D51 加预设的 `handoff`：阈值取算出的阈值和它中较小的。
- 模块页按代码写：阈值的公式、证明和各窗口的算术在 [kb-kernel](kb-kernel.md#换段阈值)，常量在 [kb-kernel](kb-kernel.md#常量)，记忆的上限在 [kb-memory](kb-memory.md#上限)，请求的输出上限在 [kb-executor](kb-executor.md#调用模型actionsts)。这里只记每个数的理由、放弃的方案和核查修掉的缺陷。设计稿第 8 节已改成指向 kb-memory 的链接。
- 每个数和理由（W 是窗口；快照里只冻结它，第 6 步起还有 `input`，见 D40）：
  - **`BYTES_PER_TOKEN` = 2**（原来 3）：中文、英文、代码在主流分词器上至少约 2 字节一个 token，估算宁可偏高。估高的代价小：只估最后一次用量之后的部分，下一次回复就给出准确用量。
  - **按实际发出的原始 UTF-8 字节估算**，不按 JSON：原来的 JSON 估算在全是换行的文本上是 2 倍，在 `\x01` 上是 6 倍。工具调用的参数仍按 JSON 算，因为它本来就按 JSON 发。
  - **`outputMax` = W/8**：模型目录常见的比例（64K/8K、128K/16K、1M/128K）。目录里有 176 个条目的 `maxTokens` 不小于窗口，也被它压住。
  - **`MESSAGE_MAX_BYTES` = 32 KiB**（原名 `TOOL_RESULT_MAX_BYTES`，值不变）：约 800 行代码。阈值为它留 16,384 token，是 64K 窗口的 25%、1M 的 1.6%。现在也限制 `decide` 写入的每条用户消息。64 KiB 会让 64K 窗口的阈值只剩 12,288，新段一开始就要换段；16 KiB 会让 `read`、`bash` 的翻页次数翻倍。
  - **`MARGIN_TOKENS` = 4096**：要放下交接指令、补的“未执行”结果、ID、消息框架和估算误差。
  - **阈值按“阈值之上要放下什么”算**，不用比例：一次回复、一个没检查的工具结果、交接说明的输出和余量（公式见 kb-kernel）。在 2 字节一个 token 的前提下，64K 到 1M 的窗口上，交接请求加交接说明都放得进窗口。
  - **段末的用户消息不进交接请求**，换段成功时原样带到新段的第一条消息：它们可能在阈值之后才到，大小不受阈值约束。
  - **记忆的三个上限**：数值和理由在 [kb-memory](kb-memory.md#上限)，在哪里检查、失败的形状在 [kb-memory 的决策](kb-memory.md#决策)。
  - `STEPS_PER_TURN` 仍是 100，占位值。
- 放弃：
  - **固定比例的阈值**（0.5 或 0.75）：比例说不出阈值之上要放下什么。原来的 0.75 不限输出；按 2 字节一个 token 算，单是交接请求的输入在 64K/8K、128K/16K、200K/64K 上就约 74K、129K、231K，都超过窗口。
  - **把模型的 `maxTokens` 冻结进快照**：它只让输出上限小的模型阈值更高（例如 gemini 从 73% 到 85.5%），正确性不需要它。
  - **在边上截断大消息**（`admit`：用省略标记代替装不下的消息；或者在 CLI、服务里截断）：标记本身让段一直变长；用户的消息可能被悄悄截成只剩标记；也管不到合并的排队消息和带过来的消息。改为在 `decide` 的 `userMessage` 里统一 `clip`，并让段末的用户消息不进交接请求。
  - **在 `loadPreset` 检查窗口够不够**：当时按 YAGNI 放弃，由 `stepLimit` 收住换段循环。v2 的工具定义和图片让固定部分更容易到阈值，第 6 步改为 `start` 和 `spawn` 的启动检查（D40）。
  - 记忆这边放弃的（在工具层检查上限、`Memory` 返回自由文本的原因），见 [kb-memory 的决策](kb-memory.md#决策)。
- 核查修掉的缺陷，每项都先写失败的测试：
  - 一次回复的工具调用太多时，补的结果会超过余量，交接请求可能超过窗口。改为不写入这条回复，本轮出错结束（[kb-kernel](kb-kernel.md#流程模型回复用途-turn)）。
  - `node:sqlite` 读 `TEXT` 在 U+0000 处截断；孤立的代理项存成 U+FFFD，量的和存的不是同一份文本；视图检查按 JS 字符串去掉旧行，在上限处覆盖会失败。改法见 [kb-memory](kb-memory.md#编码u0000-和孤立的代理项)。
  - 测试用的假记忆库不渲染真的视图，也不检查上限。测试不再断言它的视图文本。
- 没解决的风险在设计稿的[风险](../docs/design/mvp.md#风险)表：2 字节一个 token 的下限、输出上限 1/8、GPT-5 的 400K 条目、小窗口。2 字节一个 token 没在本机量过，因为本机没有缓存的分词器词表，下载要许可。后来用真模型返回的用量量过（[D24](#d24-真模型验收)）。

### D23 凭据：只读复用 pi 的凭据文件

- 状态：已确认（2026-11-15）。用户选了这个方案。
- 做法：服务把 `~/.pi/agent/auth.json` 包成 pi-ai 的 `CredentialStore`，交给 `builtinModels({ credentials })`。只交出 `type` 为 `api_key` 的条目。代码在 `src/server/credentials.ts`，怎样生效见 [kb-service](kb-service.md#启动脚本和入口)。
- 理由：
  - 用户已经在 pi 里登录过这些 provider。再要一份 key 是重复劳动。
  - **只读**：tau 不写这个文件，`modify` 和 `delete` 直接报错。写入会和 pi 抢同一个文件。
  - **不用 OAuth 条目**：OAuth 的访问令牌会过期，刷新后要写回文件。只读就做不到，所以当作没有这个条目，pi-ai 接着查环境变量。
  - **每次调用都重读**：pi 换了 key，tau 不用重启。文件不存在算没有凭据；内容不对就报错，这次模型调用失败，不悄悄退回环境变量。
  - **只支持字面量 key**：pi 的 key 还能写成 `!命令` 和 `$变量`。tau 不执行命令，也不展开变量，遇到就报错。原样发出去，等于把命令原文当 key 发给 provider。
- 放弃：
  - **只用环境变量**：要用户在启动服务的环境里再配一遍 key。
  - **tau 自己的凭据文件**：多一份要维护的秘密，没有用户需要它。
  - **复用 pi 的 OAuth**：要写回刷新后的令牌，和 pi 并发写同一个文件。
- 后果：凭据文件里某个 provider 的 `key` 非空时，pi-ai 不再看这个 provider 的 API Key 环境变量；`key` 缺失时照样读（pi-ai 逐字段合并）；`key` 是空串时，cloudflare 和 google-vertex 不读。bash 和服务以同一个用户运行，能读这个文件，符合“没有沙箱”（D7）。
- 对抗式核查后补的：JSON 报错不带文件内容（V8 的报错会引用 key 的开头）；顶层不是对象、`key` 不是字符串时报错；拒绝非字面量 key；记下 pi 写文件时的竞态和不跟随 `PI_CODING_AGENT_DIR`。细节在 [kb-service](kb-service.md#启动脚本和入口) 和 [kb-service 的坑点](kb-service.md#坑点)。

### D24 真模型验收

- 状态：默认（2026-11-15）。这是核实记录，用户还没确认。模型是 `opencode-go/deepseek-v4.1-flash`：API `openai-completions`，窗口 1M，凭据走 D23。`deepseek/deepseek-flash` 余额不足，`opencode-go/deepseek-v4-flash` 不在套餐里，都没用上。
- 量法：探针脚本直接调 pi-ai，用 tau 的 `piCredentials`、`messageBytes`、`tokens`、`usageOf`、`HANDOFF_INSTRUCTION` 和工具描述。走查用 `serve()` 起临时服务：临时库、临时预设、测试管道，模型目录和 `src/main.ts` 一样，命令走真的 CLI `main`。脚本没进仓库。
- 连续用户消息：三种形状都被接受，回答正确。一是两条连续的用户消息；二是 `[用户消息, 交接指令]`，带工具描述；三是真模型发出的工具调用和结果之后，再接两条用户消息。真服务里在“等模型”时停止再发，接口也接受了，但模型照做了被停的请求。
- 第 3 步的任务：真模型依次 `read`、`edit`、`bash`，文件确实改了。
- 第 5 步走查：带记忆的进程先 `memory_set`，下一轮用 `memory_get` 读回。它和不带记忆的进程同时运行过。停止其中一个，另一个照常结束。同一个预设的兄弟，阶段和步数在 `self` 和 `tau ps` 里一致；两次查看相隔约 2 秒，时长不可比。结束时 `effects`、`mailbox` 为空，`assertInvariants` 对所有进程成立。
- 字节估算，只在这个模型上量过。量法：一条消息的请求，减去只含一句话的请求，比较 `input + cacheRead + cacheWrite`。

  | 内容 | 字节/token |
  |---|---|
  | 英文 | 4.1 |
  | TS 代码 | 3.7 |
  | 中文文档 | 3.5 |
  | 空白缩进 | 3.2 |
  | JSON 日志 | 2.5 |
  | emoji | 2.3 |
  | 数字 CSV | 1.99 |
  | 随机符号 | 1.75 |
  | 随机生僻汉字 | 1.7 |
  | 随机十六进制、base64 | 1.4 |

  清单要的四类（中文、TS、英文、JSON 日志）都满足“下一次回复的用量不超过上一次的用量加估算”。最紧的是 JSON 日志，余 3,487 token。最后四类低于 2。
- 对抗式核查发现、已经改的：凭据的四处（D23）；`tau ps` 的时长改为向下取整，和 `self` 一样。
- 发现了、只记下的：
  - 估算误差会累加（设计稿的[风险](../docs/design/mvp.md#风险)，[kb-kernel 的坑点](kb-kernel.md#坑点)）。
  - 停止和失败不告诉模型（[kb-kernel 的坑点](kb-kernel.md#坑点)）。真服务里，被停的写诗请求在下一轮被照做了。下一条消息明说了“不用做”，也没拦住。后来修了，见 [D25](#d25-上一轮没有正常结束时下一条消息加说明)。
  - pi-ai 对“工具结果后接用户消息”没有通用的处理，D19 的说法不对。只有 openai-completions 有一个兼容开关 `requiresAssistantAfterToolResult`，默认关，内置模型都没打开。其它 API 原样发出。
- 没核实的：其它 API（`anthropic-messages`、`openai-responses` 等）；DeepSeek 直连；GPT-5 的 400K 条目；在用模型的 1M 窗口是不是真实的输入上限；用真模型换一次段。

### D25 上一轮没有正常结束时，下一条消息加说明

- 状态：已确认（2026-11-15）。用户选了“下条消息注明”。
- 问题：D24 发现，停止和失败不告诉模型。在“等模型”时停止，段末留下一条没回复的用户消息。下一轮模型看到两条连续的用户消息，会照做被停的请求。被停的请求如果要运行危险的命令，下一轮它可能被执行。
- 做法：`idle` 带的 `ended` 是 `stopped`、`stepLimit` 或 `error` 时，`decide` 在下一条用户消息前面加一句说明。文本在 [kb-kernel 的常量](kb-kernel.md#常量)，规则在 [kb-kernel 的流程](kb-kernel.md#流程每种输入)。
- 理由：
  - 不加新状态。说明由 `idle` 已有的 `ended` 算出，写进消息正文。
  - 和 `HANDOFF_HEADER`、`CARRY_HEADER` 一样，由 `decide` 写进用户消息。
  - 出错和步数用完不是用户取消的，用户多半想继续，所以这两种说明只陈述事实。
  - 出错的原因截到 1024 字节（`ENDED_REASON_MAX_BYTES`）。provider 的报错可能很长，原文由 CLI 显示给用户，模型只要知道大概。
- 停止的措辞是量出来的。模型 opencode-go/deepseek-v4.1-flash，每种措辞 4 次。场景：写诗时停止，再发一条消息。这条消息分三种：无关的问题、让它复述上一条、“继续”。
  - 无关的问题，措辞是“被停的事不要接着做，除非下面的消息要求”：4 次都写了诗。
  - 无关的问题，措辞是“上面还没回复的请求已经取消，不要再做”：3 次写了诗。
  - 无关的问题，采用的措辞：0 次。
  - 三种措辞下，说“继续”都会接着写，4 次都是。
  - 三种措辞下，让它复述上一条消息，都不写诗。
  - 真服务端到端：复述和无关消息两种场景都不再写诗。
  - 在工具运行中停止，模型本来就能看到“被中断，结果未知”。问无关的问题时，不加说明、加旧措辞、加采用的措辞，4 次都没再调用 bash。说“继续”时，三种都会接着做。
- 后来的修改（v2 第 4 步，D35）：三条说明改成设计稿 5.3 规则 6 的措辞：停止的说明不再写“用户”，说“只回应下面的信”；步数用完和出错的说明加一句，告诉模型等它回信的进程已经收到结束通知。上面的数字量的是旧措辞，新措辞的数字见下一段。
- v2 重量（2026-11-16）：
  - 量法：同上，模型 opencode-go/deepseek-v4.1-flash，用 tau 的 `start`、`decide`、`effectOf` 驱动，`createActions` 调模型（它传 `sessionId`）。“在等模型时停止”是：发出 `callModel` 后不调模型，直接喂 `stop`。每个场景在停止后寄一封信，再调一次模型。预设没有工具，没有思考级别。共调用 26 次。探针脚本在仓库外。
  - 停止，写诗时停止（设计稿 5.3 规则 6 的新措辞，各 4 次）：无关的问题 0 次写诗，4 次都只答问题。复述上一条消息 0 次写诗，3 次只复述，1 次复述后问“需要我写这首诗吗”（没写）。“继续” 4 次都接着写。
  - 先排队、再停止：写诗时先到“顺便把 1 到 20 的质数列出来”，再停止，这封信在 `endTurn` 合并进段。然后寄无关的问题，4 次都只答问题，没有人回应那封被取消的信。结论：停止的说明已经够，不用另外让模型放下合并进来的信，也不为它加说明。
  - 步数用完：寄“继续”2 次，都接着列质数；寄无关的问题 2 次，都只答问题。步数用完的场景是直接把阶段改成 `idle`、`ended` 为 `stepLimit`，段里是一问一答。
  - 出错（`stopReason` 为 `error` 的回复，写诗的请求没有回复）：寄“继续”2 次，都写了诗。寄无关的问题 4 次，4 次都写了诗，复查的 2 次都在诗后答了问题。这是想要的：出错的说明只陈述事实，没做完的请求照常做，新问题也照常答。
  - 新措辞满足“无关的问题和复述都不写诗”，所以没有再试别的措辞。采用的措辞就是上面“后来的修改”里的三条，代码和设计稿都不改。
  - 局限不变：只在一个模型上量过，每格只有 2 到 4 次。
- 放弃：
  - **写一条假的助手消息**，比如“已停止”：失败的回复不能写进段，假回复也是伪造模型的话。
  - **在 `buildContext` 里临时加**：下一轮开始后阶段就不再是 `idle`，`ended` 没了，算不出来。
  - **合并的排队消息也加**：之后的消息还会再加一次，同一轮被说两次。
- 局限：
  - 说明只是提示，模型不一定照办。只在一个模型上量过。
  - 出错和步数用完的说明没量过。
  - 换段路径没量过：写交接说明时，交接请求不带段末的消息，模型看不到停止的说明。交接说明可能写着“下一步继续做被停的事”，停止的说明紧跟在它后面。
  - “先排队、再停止”没量过：停止的说明把排队的消息也一并取消。

### D26 内核 v2 的方向和准入原则

- 状态：已确认（2026-11-16）。用户要求把内核推广后冻结，原话“能完全被上层接管不付出代价的就上层管，我们内核不管”。
- 背景：v1 只够跑单个 Agent。Pi Web 的功能要在不改内核的前提下搬到 tau 上。内核冻结以后，改动要按改契约的程序。
- 决定：
  - 方向：内核只留上层做不了、或者做了要付出代价的东西。其余放上层。
  - 准入原则：五种代价，加四条取舍顺序（第 4 条分三支）。取舍顺序归 [kb-extending](kb-extending.md#取舍顺序)。
  - 不变量：合成一张表，见 [v2 第 1 节](../docs/design/kernel-v2.md#1-目标和不变量)。
- 理由：v1 的 YAGNI 只回答“要不要做”，没回答“放在哪里”。有了取舍顺序，每个新功能都能答出按哪一条、放在哪里。
- 放弃：照 Pi Web 的功能清单逐项搬进内核。

### D28 v2 的原语

- 状态：已确认（2026-11-16）。
- 决定：v2 的做法是 actor 模型：进程有信箱，进程之间只靠信件。具体的原语：
  - 信件和发送者、安全点投递（插话）：[5.1](../docs/design/kernel-v2.md#51-信件和发送者)、[5.2](../docs/design/kernel-v2.md#52-安全点投递)。步数用完时不合并。
  - 进程之间：`post`、`spawn`、`stop_process`，回信、跳数和停止的语义：[5.3](../docs/design/kernel-v2.md#53-进程之间寄信派生停止回信跳数)。回信只覆盖一轮；顺序委派最多 16 次（D50 放宽到 512 次）；回信的头只写结束原因，规则 6 的信靠 D25 的说明纠正，不另设头。
  - 不做 `unread`：安全点并入后，异常结束、同一进程去重时，它的判定都不准。
  - 5.3 的两个规则例外：处理一条输入只读进程记录和当前工作段，加上收件人和子进程的视图；库内工具只碰库，加上 `spawn`。
  - 主动换段：`handoff` 工具（[5.4](../docs/design/kernel-v2.md#54-主动换段)）。
  - 工具定义文件，启动检查和交接以后的检查（第 6 步改 D22）：[5.5](../docs/design/kernel-v2.md#55-工具定义)。

  - 思考级别和输出上限的算法；模型请求的重试交给 pi-ai：[5.7](../docs/design/kernel-v2.md#57-调用模型思考级别和重试)。
  - 累计用量：[5.8](../docs/design/kernel-v2.md#58-累计用量)。
- 理由：上层做不到，或者上层做会不原子、丢数据，所以按取舍顺序第 4 条第 3 支进内核（[v2 第 2 节](../docs/design/kernel-v2.md#2-准入原则)末）。
- 改正：D14 里插话、派生和并发上限的前提；D17 里“删掉花费统计”。改正处已就地注明。D18 第 10 条、D22、D25 随各自的实现步改正。
- 放弃：见 D29。

### D31 第 2 步：信的头、两种形状、张数、累计用量

- 状态：已确认（2026-11-16）。
- 内容：
  - 消息的形状：有图片时，文本块可有可无。没有文本（只有图片的信、文本为空的工具结果）就不加文本块，只有图片块。理由：空文本块会被一些 provider 拒绝，也和第 1 步工具结果的做法一致。不变量因此是“字符串，或者可有可无的文本块加至少一张图片”。
  - 省略行：文本先 `clip` 到 `MESSAGE_MAX_BYTES` 减去这一行和一个换行的字节数，再接换行和这一行。没有文本时，文本块只有这一行。
  - 张数上限用在工具结果和新段第一条；空闲时收信和 `endTurn` 合并不限（入口限每封信，第 6 步）。构造函数只有两个：`userMessage` 和 `toolResult`，共用 `fit`。
  - 换段携带：只有图片的段末消息不占文本位置，`CARRY_HEADER` 照样写；带过去的文本和从前一样接在 `CARRY_HEADER` 后面。

### D47 v2 的来由：六个缺口，和 v1、v2 的对照

- 状态：已确认（2026-11-16）。从设计稿第 0 到 4 节搬来，接 [D26](#d26-内核-v2-的方向和准入原则)、[D28](#d28-v2-的原语)。设计稿那几节只留链接。
- 一句话：**进程是带持久信箱的 actor。所有输入都是信件，信件来自人或别的进程。**
- 缺口：v1 上，Pi Web 的功能只能放在上层，而且有代价。代价来自六个缺口：
  1. **只有一种发送者，投递太晚。** 内核只认用户。运行中到的信要排队到本轮结束。所以进程之间没法原子地发消息，也没法插话。
  2. **进程不能管进程。** 进程不能建进程、不能停别的进程，也拿不到别的进程的结果。
  3. **工具和内容是写死的。** 工具列在 `tools.ts` 里，内容只有文本。所以上层加不了工具，图片进不来。
  4. **调用模型的参数是写死的。** 预设不能设思考级别，tau 也不重试。Pi Web 的角色几乎都开着思考，Pi SDK 默认会重试。这两样上层都碰不到。
  5. **累计用量没有来源。** 交接回复和没写进段的回复，用量哪里都没存。
  6. **上层看不到过程。** 协议只有 `start`、`send`、`stop`、`ps`。读不了历史，也不能订阅变化。
- 对照：

  | 概念 | v1 | v2 |
  |---|---|---|
  | 输入 | 用户消息、模型结果、工具结果、停止 | 信件、模型结果、工具结果、停止 |
  | 谁能写信 | 用户 | 用户、进程 |
  | 运行中到的信 | 排队到本轮结束 | 排队到下一个安全点 |
  | 进程能对别的进程做什么 | 什么都不能 | 寄信、派生、停止；派生和要回信的信会收到回信 |
  | 有哪些工具 | 写死在 `tools.ts` | 内置工具，加工具定义文件 |
  | 内容 | 文本 | 文本和图片 |
  | 调用模型 | 不传思考级别，不重试 | 按预设传思考级别；拿到成功的响应之前的失败由 pi-ai 重试 |
  | `decide` 输出什么 | 新记录、要追加的消息 | 再加要寄出的回信 |
  | 进程记录 | v1 的字段 | 再加父进程、累计用量 |

- v2 的类型以 [kb-kernel](kb-kernel.md#状态) 和代码为准，这里不再抄。阶段还是 3 个，`Phase` 的形状不变，只有 `Turn` 多了字段；只在运行中有意义的新数据都放在 `turn` 里。`Env` 不变。

  - 每个原语都写出“上层做的代价”。写不出来，它就放上层（现在写在 [kb-contract 的原语和它在内核的理由](kb-contract.md#原语和它在内核的理由)）。

  - 需求取自 Pi Web：`E:\piweb` 的 README 和 kb 说明有哪些功能，本机的 Pi Web 会话记录说明用过没有。（2026-11-16 就地改正：当时只统计了 `E:\` 下一层的 7 个 `.piweb` 目录。全部是 17 个项目、191 个会话，见 [D54](#d54-使用数据重核)。）

### D49 fork 进内核

- 状态：已确认（2026-11-16）。用户在冻结之前决定：fork 进内核。改了 [D46](#d46-v2-也不做的) 第一张表的一行（原来写“本机没用过”）。
- 证据：
  - 本机 Pi Web 的 fork 用过 4 次：`E:\godot\actor` 3 次（2026-09-13 到 09-14），`E:\godot\arch\miniArch` 1 次（2026-10-03，源会话还在）。都是用户在界面上发起，从某条消息分叉（Pi Web 记了 `sourceConversationId`、`sourceLeafId`、`forkedAt`），带着完整上下文继续工作；actor 第三个分支之后有 1,688 条记录。actor 的 3 个源会话后来都删了。（2026-11-16 就地改正：原写 3 次、都在 actor，漏了 miniArch，见 [D54](#d54-使用数据重核)。）
  - 设计稿原来写“本机没用过”，是因为当时只统计了 `E:\` 下一层的项目，漏了 `E:\godot\*` 和第三层的 `E:\godot\arch\miniArch`。
- [取舍顺序](kb-extending.md#取舍顺序)逐条：
  1. 第 1 条不成立：fork 不违反那几条规则。它不算旁路：和 `start` 一样，只在边上建一个新进程，结果由纯函数 `fork` 算出。它不改任何已有进程，新进程之后的变化都走运行循环。建进程的请求是 `start` 和 `fork`。
  2. 第 2 条不成立：用过 4 次；tau 没有别的机制满足“从某条消息分叉重来”。
  3. 第 3 条不成立：上层只能用 `history` 读出，再 `start`。第一封信最多 `MESSAGE_MAX_BYTES`（32 KiB），带不过去完整的段。这是“做不到”。
  4. 第 4 条第 1 支不成立，内核版不推翻不变量：
     - fork 是协议请求，不是处理一条输入。它读源进程的当前段，和 `history` 一样。不变量 9 管的是处理一条输入。
     - 新进程复制源进程冻结的快照（不变量 6）。
     - 新进程从一开始就是这些消息，不是缩短一个已有进程的上下文，所以不碰不变量 8。
     - 数据只增（不变量 10）：不删不改任何东西，图片引用照用，`blobs` 只增。
  5. 第 4 条第 2 支不成立：代价出在用过的部分。
  6. 第 4 条第 3 支：进内核。
- 做法：
  - 协议请求 `{ op: "fork"; process: string; before?: number }`（后来加了可选的 `preset`，见 [D52](#d52-fork-带-preset给进程换角色)）。`before` 是源进程当前段里一条用户消息的段内序号，就是 `history` 每行的 `seq`。
  - 新进程的每个字段、拒绝的情形：[kb-kernel 的 fork](kb-kernel.md#fork)。事务：[kb-store 的存储事务](kb-store.md#存储事务)。请求、回执和订阅：[kb-service 的线协议](kb-service.md#线协议srcprotocolts)。
  - 纯函数 `fork` 在 `src/kernel/decide.ts`，和 `start` 放在一起；事务 `forkProcess` 在 `src/store/inputs.ts`；服务不调用 `pump`。
  - CLI 不变，不加命令。上层的 `tx` 以后加 `fork` 子命令（[kb-extras](kb-extras.md#上层的命令行-tx)）。
  - `state_json` 的形状、表结构、`SCHEMA_VERSION` 都不变。
- 选择：
  - 只复制当前段，不复制旧段。换过段的源进程，新进程的第 1 段是源进程当前段的前缀，它的第一条是交接说明。
  - 不带 `preset` 时不换预设，原样复制快照。换角色的两份代价里，带不过去完整上下文那份后来由 `fork` 的可选参数 `preset` 解决，见 [D52](#d52-fork-带-preset给进程换角色)。
  - 带 `before` 时在用户消息之前切。理由：前面一定停在一轮的结尾或一批工具结果之后，所以源进程正在运行也能 fork；不带 `before` 要求源进程 `idle`，因为运行中的段末尾可能是一条还没有结果的工具调用。

### D52 fork 带 preset：给进程换角色

- 状态：已确认（2026-11-16）。用户在冻结之前决定：`fork` 加可选参数 `preset`。用户知道下面“证据”里第二条，仍然决定要做。
- 证据：
  - 本机 Pi Web 换角色共 27 条记录。去掉 2 到 4 秒内换过去又换回来的，真正在对话中途换了并接着干活的有 17 次（16 次换了模型）。其中 15 次，第一次请求就带着 4 万 token 以上的上下文；15 次在 6 分钟内跟着一条短消息接着干。

- [取舍顺序](kb-extending.md#取舍顺序)逐条。换角色有两份代价，分开答：
  1. “ID 变了”（子进程的回信和笔记留在旧进程）：仍按第 4 条第 1 支（要推翻不变量 6），留给上层，见 [kb-extras](kb-extras.md#pi-web-的功能在-v2-上的做法)。这份没变。
  2. “只带摘要，带不过去完整上下文”：上层能做的只有 `start` 一个新进程，让它按需用 `history` 读回旧段。这条路慢而且失真：每次最多 32 KiB，调用成倍，原来的工具调用变成文本。按第 4 条第 3 支，进内核，做成 `fork` 的预设参数。
- 做法：
  - 协议请求 `{ op: "fork"; process: string; before?: number; preset?: string }`。不带 `preset` 的 `fork` 一个字都不变。
  - 带 `preset` 时服务在事务之外读这个预设（和 `start` 一样用 `loadPreset`，含工具定义），读不出回 `error`。
  - 新进程的快照是这个预设新冻结的；`segment.memoryView` 按新预设重取（和 `spawn` 一样，读新预设的记忆库），不用源进程的。其余字段、复制的消息按 `before` 的规则取，和不带时一样。
  - 新模型不收图片：复制的消息里每张图在原位置换成已有的说明 `IMAGE_UNSUPPORTED`，和同一条消息里的文字用换行连成一段。用户消息成字符串，工具结果成一个文本块，所以消息的两种形状不变。新模型收图片则原样。
  - 大小检查：用不带锚点的估算（系统提示词、工具描述和全段按字节，图片按 `IMAGE_TOKENS`，就是 `contextUsed` 没有用量锚点时的式子，按新进程算）。估算要低于新预设的换段阈值（含 `handoff`），否则拒绝，报出估算和阈值。不能用 `contextUsed` 的锚点：锚点是旧模型、旧固定部分的用量。理由：超过阈值时，新进程的第一次调用就是交接调用，带着整段，换到小窗口会失败。启动检查照做。
  - 校验和算新进程在纯函数层（`fork` 多一个参数 `to`），存储层只读写；读预设和读记忆在纯函数层之外。细节：[kb-kernel 的 fork](kb-kernel.md#fork)、[kb-store 的存储事务](kb-store.md#存储事务)、[kb-service 的线协议](kb-service.md#线协议srcprotocolts)。
  - 不改：CLI、表结构、不带 `preset` 的 `fork`、`state_json` 的形状（快照本来就是 `PresetSnapshot`），所以 `SCHEMA_VERSION` 不动。
  - `IMAGE_UNSUPPORTED` 从 `src/store/blobs.ts` 挪到 `src/kernel/context.ts`：纯函数层不能导入存储层，存储层和工具定义改从那里导入。
- 选择：
  - 超过阈值就拒绝，不自动裁剪：裁剪就是缩短上下文，只有换段能做（不变量 8）。要换到小窗口，先在源进程里换段，或者带 `before` 少复制一些。
  - 拒绝用 `>=`：和换段的判断一致，估算等于阈值就是已经该换段。
  - 估算偏高（按字节，宁可估高），所以刚好放得下的段可能被拒。可以接受：被拒的出路明确，放行后失败的出路没有。
- 这是改契约（协议请求、`fork` 的行为）。程序见 [kb-contract](kb-contract.md#改契约的程序)：上层为什么做不到见上面第 2 条；推导测试在冻结的最后一步做，题目以冻结时的文档为准，文档已含这一项，所以没有单独为它重测。
- 测试：
  - 纯函数（`test/kernel/fork-preset.test.ts`）：快照和记忆视图来自新预设，源不变；图片换成说明、形状对；估算刚好低于能建、等于被拒；用 `contextUsed` 的锚点会放行而估算会拒绝的反例；带 `before` 照旧。
  - 存储层（`test/store/fork.test.ts`）：快照和记忆视图来自新预设，库里别的行不变；新模型不收图片时换成说明，收图片时原样，`blobs` 不增；放不进和启动检查不过，什么都不建。
  - 服务（`test/server/protocol.test.ts`）：之后对新进程 `send`，模型收到新预设的系统提示词、工具描述和复制的消息，源不变；读不出的预设、放不进的预设、类型不对，回 `error`，什么都不建。

### D59 删除原语：旧段和空闲进程

- 状态：已完成（2026-11-16）。推导测试第四到六次（[D60](#d60-推导测试第四次)、[D61](#d61-推导测试第五次)、[D62](#d62-推导测试第六次)）没通过，文档已补；三次的错处都和删除原语无关。用户决定不等推导测试通过就合并，见下面的“破例”。用户原话：“我在考虑要删旧段，不能让占用无限增长，至少要提供管理这些陈旧东西的原语”“由上层自行管理”“prune 可能需要保留最近n段”“Ok”。这是冻结以后第一次改契约，按[改契约的程序](kb-contract.md#改契约的程序)做：先写理由，推导测试通过，再改。
- 为什么改：
  - tau 要连续运行很多年。不变量 10（数据只增）之下，库只长不缩。本机 Pi Web 4 个月、191 个会话共 405.7 MB，其中 58% 是压缩边界之前的旧数据（[kb-piweb-lessons](kb-piweb-lessons.md#一个文件混装三种寿命)）。Agent 删过约 70 个会话（直接调用 42 次，脚本里 28 次）。
  - 只删旧段，增长只是变慢：临时 Agent 越派越多，每个都留着记录和当前段，`ps`、`self` 也随进程数变慢。所以进程也要能删。
  - 上层一点都做不了：库里的东西只有内核能删（[D46](#d46-v2-也不做的) 第二张表）。按取舍顺序这是第 4 条第 1 支，原本不做；用户决定改不变量。
- 决定：内核只给三个原语，各是一个协议请求、一个事务。`prune`、`remove` 提交之后回 `receipt`，`sweep` 回一行 `swept`。删什么、什么时候删，由上层定（同 [D58](#d58-项目的上下文由上层拼) 的口径）。
  1. `prune`（`process`、`before`）：删这个进程段号小于 `before` 的旧段。当前段永远不删；`before` 大于当前段号回 `error`。进程在运行也可以删，因为处理输入只读当前段。按主键前缀删，不随库变慢。
     - 保留最近 n 段：上层从 `ps` 读当前段号 c，传 `before` = c − n + 1。读完到请求之间进程换了段，只会多留一段，不会多删。
     - 不另设 `keep` 参数：`keep` 只能按事务那一刻的当前段算。上层先用 `history` 存档再删时，中途换了段，就会删掉还没存档的那一段。
  2. `remove`（`process`）：删一个进程的记录和全部段。下面任何一条成立就回 `error`，什么都不删：
     - 不是空闲，或者信箱里有它的输入。
     - 有进程的 `parent` 是它。上层要先删子进程，从叶子删起。
     - 它在任何进程的 `turn.replyTo` 里，或者在排队的信（任何进程的 `turn.queued` 和信箱）的 `replyTo` 里。
     - 执行器里还有这个进程的动作没收尾（停止以后，被中止的动作还没结束）。理由：动作收尾（`complete`）按 (进程 ID, n) 找行。进程删了、ID 又被新进程碰上，旧动作的结果会落进新进程。执行器为此给一个只读的查询 `busy(id)`：它的中止开关表里有没有这个进程的键。崩溃以后没有这样的动作，所以只有服务活着时才有这一条。
     前面几条在同一个事务里重新读全部进程记录和信箱来判断，和 `self` 一样读全部记录。执行器那一条不在库里，由服务在调用事务之前查。
  3. `sweep`：清掉没人引用的图片，提交之后回一行 `swept`（删掉的行数）。引用在三处：全部进程的全部段、信箱、进程记录里的 `turn.queued`（[kb-store 的存储层不变量](kb-store.md#存储层不变量)第 8 条）。找引用按原文找 `blob:` 加 64 位十六进制：多认只会多留，不会多删。扫一遍收齐引用，再删其余的行。它要扫全库，期间服务停着不处理别的事，所以和前两个分开：上层批量清理完，再调一次。没人引用的图片本来无害（[kb-store 的图片](kb-store.md#图片)），分开不损失原子性。
- 为什么这样就不用改投递规则：被删的进程不再被任何地方引用。删了以后，新的引用也指不到它：`post`、`stop_process`、`send`、`fork` 都先查进程在不在，`spawn` 和 `start` 只建新 ID。所以回信永远寄不到已删的进程，`decide` 照旧不查收件人，AGENTS.md 的“两个例外”不变。新进程碰巧拿到已删的 ID 也无害：没有东西还指着它，执行器也没有它的动作。
- 为什么不算旁路（[核心原则](kb-extending.md#核心原则)第 1 条）：三个请求不改任何进程的状态。状态是进程记录加当前段，`prune` 只删旧段；`remove` 只删空闲、没人引用的进程，删掉以后它不再有变化；`sweep` 只删没人引用的图片。和 `start`、`fork` 一样，是运行循环之外的例外。
- 跟着改的规则：
  - `history` 读已删的段回 `error`。判据是段号小于当前段、条数为 0：旧段从不为空，写进存储层不变量并加测试。
  - `watch`：删进程时，给订阅推一行 `removed`，订阅这个进程的连接随后关闭。
  - 存储层不变量第 8 条的检查 `assertBlobRefs` 扩到全部段，不只当前段。
- 不做：
  - 删记忆：记忆按预设分库，每个库本来就有上限（[kb-memory](kb-memory.md#上限)）。
  - 自动清理、保留策略：上层定。
  - 缩小库文件：SQLite 删掉的页会被新数据复用，库就不再长。要缩小，停服务做一次 `VACUUM`。
  - 删一段里的一部分、删单条消息：只按整段删。
- 要改的契约和文档：
  - 不变量 10；线协议的 `Request`、`Reply`（加 `prune`、`remove`、`sweep` 和推送的 `removed`、回的 `swept`）；`history` 的拒绝条件；事务清单从四个变成七个；风险表“库越长越大”；D46 第二张表那一行移出。
  - 设计稿 `mvp.md` 的“MVP 不做”（“删除旧工作段”“彻底删除”）和风险表“进程永不删除”。
  - kb-kernel 的“收件人不查是否存在：进程不删除”改成上面的理由；kb-store、kb-service、kb-executor 里写着“永不删除”“只增不删”的地方，kb-executor 的“编号只增不减”一句；kb-extras 加一行上层的清理。
  - `tau` 的命令行冻结在 v1，上层用协议。

### D63 上层的依赖随便加

### D64 内核的自由度：给上层事实、对称的控制和可组合的动作

- 状态：已决定（2026-11-17），用户定的。这是冻结以后第二次改契约。推导测试第七次（[D65](#d65-推导测试第七次)）、第八次（[D66](#d66-推导测试第八次)）没通过，文档已补；第九次（[D67](#d67-推导测试第九次)）通过。用户原话：“有道理，你直接带队实现吧，目的是给上层提供更多的可组合功能，而不是总需要去改内核，这需要内核提供足够的自由度”，“允许增长内核代码行数”。
- 为什么改：
  - 冻结以后，上层每撞上一类新需要，都只能申请改内核。原因有两个：内核对外给的多是结论，不是事实；外面能做的控制也比模型少。
  - 投影只给筛过的几个字段。排队的信、谁在等回信、跳数、离换段多远，界面都给不了（[界面设计稿第 11 节](../docs/design/gui.md#11-不显示的)）。进程用的是哪份快照，界面只能读当前的预设文件去猜。
  - 信写进段以后只剩文字。上层只能照抄信头的格式，用正则拆。一批里只有用户的信时不加头，所以以“（来自进程…）”开头的用户信会被认错。
  - 调用模型的参数只认 `thinking` 和 `handoff`。[D46](#d46-v2-也不做的) 第一张表有三行写着“上层碰不到，要改内核”。
  - 能原子执行的只有内置的库内工具。codemode 脚本调不到记忆和 `spawn`。上层要包一层“带限额的派生”，只能把原始的 `spawn` 也给模型。
  - 外面不能换段：界面的换段按钮只能写信，请模型调 `handoff`。外面也读不了、改不了记忆。
  - 界面自己写了一份预设解析。内核的预设一加字段，它就坏。
  - 普查（2026-11-17）：四个来源（界面、上层的做法和不做清单、总管 Agent 的设想、内核自身的读写对称）找到 68 条缺口。每个候选原语都有一位 Opus 做对抗式审阅，最后还有一位挑刺。
- 新的准入原则：内核对上层的形状。共四类，按类判，不按单个功能的用量判（[kb-extending 的核心原则 8](kb-extending.md#核心原则)）：
  1. **事实可读**：内核持有的持久事实，上层都能经协议原样读到。这些事实包括进程记录、段里每条消息的来历、记忆、图片、预设怎样读成快照。投影是给模型和人的摘要，不是唯一的读法。
  2. **控制对称**：模型能对进程做的控制，外面也能做。包括寄信、要回信、换段、停止、派生、读写记忆。
  3. **动作可组合**：库内动作，工具定义能在结果里声明，和工具结果在同一个事务里执行。
  4. **参数可传**：调用模型的参数，凡是 pi-ai 的 `streamSimple` 转发、又不归内核管的，预设都能写。
  - 补齐这四类的原语，不要求“本机用过”。功能本身照旧按 YAGNI 和[取舍顺序](kb-extending.md#取舍顺序)判，判的时候把这些原语当成已有的。
  - 以后内核加一样事实或控制，默认同时给上层。加库内工具时，在“能声明的库内动作”里列上它；记录加字段，`inspect` 自动读得到。
- 原语，共 11 组（细节在各模块页，见下面的规格）：

  | # | 原语 | 类 | 上层做的代价 |
  |---|---|---|---|
  | 1 | `inspect`：原样读进程记录 | 事实 | 做不到。冻结的快照、排队的信、`replyTo`、跳数只在记录里，上层又不读库（[D63](#d63-上层的依赖随便加)） |
  | 2 | 限度：投影带换段阈值；`check` 干跑预设的读取和启动检查 | 事实 | 做不到不漂移。阈值和固定部分要内部常量和模型目录，上层抄一份解析就会漂移 |
  | 3 | 段里的消息带结构（`tau` 字段） | 事实 | 丢数据。信并进段以后，发送者、边界、跳数、`replyTo` 只剩文字，或者没了 |
  | 4 | 进程记录的 `since` | 事实 | 做不到。模型出错或被停止时段里不写消息，进入当前阶段的时刻从段里算不出来 |
  | 5 | `watch` 推追加的消息；流式预览带种类 | 事实 | 慢：每走一步，上层都要再 `history` 一次。看不见：思考和工具调用的流 |
  | 6 | 记忆走协议：`memory`、`memory_write` | 控制 | 做不到。只能起一个进程让模型去读写，既花钱，结果也进段 |
  | 7 | 换段信：`send` 带 `handoff` | 控制 | 做不到：模型可以不照做，运行中也不能用。慢：要三次模型调用 |
  | 8 | `send` 带 `from`、`reply` | 控制 | 丢数据、不原子。一轮的结果要上层盯着再转寄，上层没在运行时就漏了 |
  | 9 | `start`、`fork` 带调用方定的 `id` | 控制 | 不原子。回执丢了再重试，会多建一个进程 |
  | 10 | 工具定义在结果里声明库内动作 | 动作 | 不原子。工具里用 `tau send/start/stop`，崩溃后模型重做，信会重复，子进程会多一个（[原语表](kb-contract.md#原语和它在内核的理由)“进程之间”一行） |
  | 11 | 预设的 `options` | 参数 | 做不到。调用模型的参数，上层碰不到 |

- 规格：每组的字段、检查顺序、拒绝的情形和崩溃语义在模块页，以代码和测试为准。下面每组只留概括和链接。
  1. `inspect`：原样读进程记录，带当前段条数和限度，不开事务，不调 `pump`。不做“`watch` 推原样记录”。见 [kb-service](kb-service.md#读记录和干跑inspectcheck)。
  2. 限度和 `check`：`limits(快照)` 给出固定部分、记忆上界和换段阈值，`startError` 用它；`check` 用 `start` 同一个读预设的函数干跑。读预设时的任何拒绝只许加在 `loadPreset`、`loadToolDefs`、`startError` 里，这样 `check` 和 `start` 永远一致。见 [kb-kernel](kb-kernel.md#常量)和 [kb-service](kb-service.md#读记录和干跑inspectcheck)。
  3. 段里的消息带结构：用户消息和补的工具结果带可选的 `tau`，`buildContext` 发请求前去掉，给模型的文字不变。见 [kb-kernel](kb-kernel.md#tau消息带的结构)。
  4. `since`：进程记录加可选的 `since`，`decide` 写 `env.now`，仍是纯函数。见 [kb-kernel](kb-kernel.md)的 `since` 一条。
  5. `watch` 的 `messages: true` 推追加的消息；流式文本的 `kind` 区分思考和工具调用，只推给带 `messages: true` 的订阅。见 [kb-service](kb-service.md#历史和订阅)和[流式文本](kb-service.md#流式文本)。
  6. 记忆走协议：`memory` 读，`memory_write` 整批带版本号写，是第 8 个存储事务 `writeMemory`。记忆不是进程状态，所以不算旁路。不做 `memory_view` 和单键的 `memory_get`。见 [kb-service](kb-service.md#读写记忆memorymemory_write)、[kb-memory](kb-memory.md)和 [kb-store](kb-store.md#存储事务)。
  7. 换段信：`send` 带 `handoff`，三个时机、生效条件和作废的情形见 [kb-kernel](kb-kernel.md#换段信)。不变量 (a)(b) 两条蕴含见 [kb-kernel 的不变量](kb-kernel.md#不变量)。
  8. `send` 带 `from`、`reply`：以进程的名义寄信，发送者和跳数从它的记录构造，不能伪造回信。见 [kb-store](kb-store.md#存储事务)和 [kb-service](kb-service.md#调用方定的-id-和以谁的名义寄信)。
  9. 调用方定的进程 ID：`start`、`fork` 的 `id`，已存在就拒绝，重试幂等。见 [kb-service](kb-service.md#调用方定的-id-和以谁的名义寄信)。
  10. 工具定义在结果里声明库内动作：`call` 项、个数上限、执行条件、能声明的名单、失败和崩溃语义见 [kb-tools](kb-tools.md#运行工具定义)、[kb-store](kb-store.md#声明的库内动作)和 [kb-executor](kb-executor.md#运行工具actionsts)。不推翻不变量 4：这是结果里的声明，不是脚本中途调用。[D36](#d36-第-4-步第二部分进程之间的工具的执行和两处例外) 的两处读取例外，触发点多了声明的动作。[风险表](kb-contract.md#风险表)“子预设没有 agents”那一行，加上声明 `spawn` 的工具定义。
  11. 预设的 `options`：白名单、类型、大小上限和拒绝的类别见 [kb-kernel](kb-kernel.md#预设选项)，执行器的铺法见 [kb-executor](kb-executor.md#调用模型actionsts)。白名单跟着 pi-ai 加键，算放宽，不算改契约。做不到的照实写：原生的服务层级（只能经 `samplingParams.service_tier` 用在兼容 OpenAI 的适配器上）、各家 provider 的专有字段、按轮改参数、换段时用另一个模型。
- 演进规则（契约）：
  - `Process`、`PresetSnapshot`、`Letter`、`Turn`、`Request`、`Reply` 和段里消息的 JSON，以后只加可选键。客户端忽略不认识的键。删字段、改名、改语义，按改契约做。
  - 这次加的都是可选键，所以 `SCHEMA_VERSION` 不变。旧行没有这个键，就等于没有，不写兼容代码。
- 不做：
  - `watch` 推原样记录。
  - `memory_view`、单键的 `memory_get`。
  - `check` 收预设草稿；“全部预设”模式。
  - `start` 带 `from`、`reply`、`handoff`；`post`、`spawn` 带 `handoff`。
  - 跨请求的批量事务（`batch`）。有了第 9 条的 ID 和 `memory_write` 的整批，常见的多步操作已经能安全重试。
  - 停一棵树而不唤醒祖先；只停指定的一轮。这两样的投递语义在 `decide` 里，本机没出现过它们的代价。
  - 为什么这几样不算四类自由度没补齐：`watch` 推原样记录、`memory_view`、单键的 `memory_get`、`check` 的两种扩展，事实已经能经 `inspect`、`memory`、`check` 读到，只是换一种读法；`start` 不带 `from`、`reply`、`handoff`，因为新进程的段是空的，没有可交接的内容，第一封信也没有在等的一轮，要回信的派生用 `spawn` 或声明的 `spawn`；`batch` 和两种停止的语义不是“事实”或“已有的控制”，是新的行为，属于下面“还只能改内核的类别”。
  - 推翻 D29 的一条：D29 写“不做协议的发送者字段”，第 8 组加了 `from`。`from` 只收进程 ID，不是进程的来源照旧用正文前缀。
- 加完以后，还只能改内核的类别。以后有这类需要，先读这里：
  1. 改已有进程的快照而 ID 不变：换预设、模型、参数，模型故障切换。要推翻不变量 6。
  2. 新的投递和回信语义：多层自动上交、回信给第三方、不唤醒、只停一轮、停止时不唤醒祖先。
  3. 模型看到的内容怎样拼：固定文字、系统提示词的拼法、内置工具的描述、记忆挂载、压缩。
  4. 模型接入：OAuth、自定义 provider、`streamSimple` 不转发的参数、按轮改参数、换段时用另一个模型。
  5. 新种类的库内动作：在工具里原子地 `fork`、`remove`、`prune`，进程之间寄图片。内核以后每加一个库内动作，就把它列进“能声明的库内动作”。
  6. 执行策略：模型调用的并发上限、暂停认领、只中止工具而让这一轮继续、在 `spawn` 或认领时挡的硬上限。
  7. 跨请求的原子组合。
  8. 在内核里等外部事件（阶段固定 3 个）。
- 代码量预算：用户允许增长。从 3000 行放宽到 3600 行，实现完按实际行数校准。

| 默认值 | 理由 |
|---|---|
