# tau 内核 v2 契约（设计稿）

`status: 定稿（第六版），按第 9 节实现` · `updated: 2026-11-16`

## 0. 这份稿子管什么

- 本稿提出内核 v2 的契约：把内核推广成少数几个通用原语，实现以后冻结。
- 审阅通过以后，按[第 9 节](#9-实现顺序)的顺序实现。每做完一步，细节移进对应的 kb 页，本稿只留链接。这和 [MVP 设计稿](mvp.md)的做法一样。
- 现有机制以 kb 页为准。本稿只写要改什么、为什么改。
- 本稿说的“内核”是 tau 自己：`src/` 的代码，加上它的文件格式、协议和 CLI。和它相对的是“上层”。`src/kernel/` 叫“纯函数层”（第 7 节第 0 步统一用词）。

## 1. 目标和不变量

目标：

1. 冻结内核契约。以后 Pi Web 那类功能都在上层做，不再改内核。
2. 功能放在上层，不因此变差：仍然原子、持久、看得见，崩溃后说得清。
3. 内核只做上层做不了、或者做了要付出代价的事（[第 2 节](#2-准入原则)）。
4. 仍然遵守 YAGNI：只为真实用过的功能加原语。
5. 判据：推导测试通过（[第 9 节](#9-实现顺序)第 8 步）。只读文档的 Agent（Sonnet、Haiku 级别）能把文档没写过的新功能放对地方。

不变量。这是 v2 实现以后的样子，已经含 v2 自己的新增和例外。第 2 节的取舍顺序按这张表判断，第 10 节把它冻结：

1. 3 个阶段：`idle`、`awaitingModel`、`awaitingTool`。
2. 2 种副作用：调用模型、运行工具。工具分库内和库外。
3. `effects` 表和信箱的结构。
4. 一条输入一个事务。`decide`、`effectOf`、`observe` 是纯函数。
5. 崩溃后，库外动作报“被中断”，不自动重做。
6. 快照冻结：进程是一份启动时冻结的预设快照。
7. 回信只在一轮结束时寄出，每个进程一封（5.3 的规则 4）。信的 `replyTo` 并进哪一轮（规则 1），就由那一轮结束时回，之后的几轮不回。信还在排队时这一轮异常结束，也在这一轮结束时回。
8. 换段是唯一缩短上下文的办法。图片有一个例外（5.6）。
9. 处理一条输入不读旧段，也不读别的进程的工作段。
10. 数据只增：进程、旧段、图片都不删。
11. 服务只在命名管道上监听。

另外不变的规矩：依赖白名单；代码量预算 3000 行（[第 7 节](#7-要改的规则)）。

## 2. 准入原则

五种代价、四条取舍顺序（第 4 条分三支）和“怎样用这个顺序”，见 [kb-extending 的取舍顺序](../../.knowledge/kb-extending.md#取舍顺序)。核心一句：上层能完整接管、不付出代价的功能，内核不做。

写法的要求：

- 第 5 节的每个原语都写出“上层做的代价”。写不出来，它就放上层。
- 第 6、8 节的每一行都写明按哪一条归类。第 8 节写“没有代价”时，要说出为什么五种都不沾。
- 需求取自 Pi Web：`E:\piweb` 的 README 和 kb 说明有哪些功能，本机的 Pi Web 会话记录说明用过没有。
- 现在就把原语定全，不等每个功能出现再改内核。原因：内核要冻结，契约就得一次定全。

v2 的原语都按第 4 条第 3 支进内核：5.1、5.2、5.4、5.5、5.6、5.9 和 5.7 的思考级别，上层做不到；5.3、5.8 和 5.7 的重试，上层做会不原子或丢数据。

## 3. 现在的缺口

v1 上，Pi Web 的这些功能只能放在上层，而且有代价。代价来自六个缺口：

1. **只有一种发送者，投递太晚。** 内核只认用户。运行中到的信要排队到本轮结束。所以进程之间没法原子地发消息，也没法插话。
2. **进程不能管进程。** 进程不能建进程、不能停别的进程，也拿不到别的进程的结果。
3. **工具和内容是写死的。** 工具列在 `tools.ts` 里，内容只有文本。所以上层加不了工具，图片进不来。
4. **调用模型的参数是写死的。** 预设不能设思考级别，tau 也不重试。Pi Web 的角色几乎都开着思考，Pi SDK 默认会重试。这两样上层都碰不到。
5. **累计用量没有来源。** 交接回复和没写进段的回复，用量哪里都没存。
6. **上层看不到过程。** 协议只有 `start`、`send`、`stop`、`ps`。读不了历史，也不能订阅变化。

## 4. v2 的心智模型

一句话：**进程是带持久信箱的 actor。所有输入都是信件，信件来自人或别的进程。**

| 概念 | v1 | v2 |
|---|---|---|
| 输入 | 用户消息、模型结果、工具结果、停止 | 信件、模型结果、工具结果、停止 |
| 谁能写信 | 用户 | 用户、进程 |
| 运行中到的信 | 排队到本轮结束 | 排队到下一个安全点 |
| 进程能对别的进程做什么 | 什么都不能 | 寄信、派生、停止；派生和要回信的信会收到回信 |
| 有哪些工具 | 写死在 `tools.ts` | 内置工具，加工具定义文件 |
| 内容 | 文本 | 文本和图片 |
| 调用模型 | 不传思考级别，不重试 | 按预设传思考级别；拿到成功的响应之前的失败由 pi-ai 重试 |
| `decide` 输出什么 | 新记录、要追加的消息 | 再加要寄出的回信 |
| 进程记录 | v1 的字段 | 再加父进程、累计用量 |

类型草图（只写变化）：

```ts
type Sender =
  | { kind: "user" }
  | { kind: "process"; id: ProcessId; preset: string; reply?: { ended: Ended } };   // reply 有值：这是回信

type Content = TextContent | ImageContent;   // pi-ai 1.0.0 的类型；图片的 data 写成 "blob:<hash>"

interface Letter {
  from: Sender;
  content: Content[];
  hops: number;              // 跳数，见 5.3
  replyTo?: ProcessId;       // 处理这封信的那一轮结束时，把最终回复寄给它，见 5.3
}

type Input =
  | { kind: "letter"; letter: Letter }                       // 取代 userMessage
  | { kind: "modelResult"; n: number; outcome: ... }         // 不变
  | { kind: "toolResult"; n: number; outcome: ... }          // 内容可以带图片
  | { kind: "stop" };                                        // 不变

interface ToolResultContent { content: Content[]; isError: boolean }   // v1 只有 text

interface Turn { steps: number; queued: Letter[]; hops: number; replyTo: ProcessId[] }

interface Usage { input: number; output: number; cacheRead: number; cacheWrite: number }

interface Process {
  /* v1 的字段 */
  parent?: ProcessId;        // 建好后不变
  usage: Usage;              // 累计用量，见 5.8
}

interface PresetSnapshot {
  /* v1 的字段：id、workdir、model、tools、prompt、contextWindow。tools 还能写 agents 和工具定义的名字 */
  thinking?: ThinkingLevel;      // pi-ai 的思考级别，不写就不传，见 5.7
  input: ("text" | "image")[];   // 模型能收的输入，启动时从 pi-ai 的模型目录冻结，见 5.6
  toolDefs: ToolDef[];           // 用到的工具定义，启动时冻结，见 5.5
}

interface ToolDef {
  name: string; description: string; parameters: object;
  command: string; timeout: number; output: "text" | "content";
}

interface ProcessView { /* v1 的字段 */ parent?: ProcessId }

interface Projection {
  now: Instant;
  self: ProcessView & {
    segment: number;
    messages: number;                    // 当前段的消息条数
    segmentAge: number | null;
    context: { used: number; window: number };
    usage: Usage;
  };
  siblings: ProcessView[];               // 同一个预设下运行中的其他进程，同 v1
  children: ProcessView[];               // 运行中的子进程
  idleChildren: number;                  // 空闲的子进程个数
}

function decide(p, seg, input, env): {
  process: Process;
  append: Message[];
  out: { to: ProcessId; letter: Letter }[];                 // 回信
};
```

- 阶段还是 3 个，`Phase` 的形状不变，只有 `Turn` 多了字段。只在运行中有意义的新数据，都放在 `turn` 里。
- `Env` 不变。
- 投影里出错的原因用 5.1 的结束原因函数截短。

## 5. 原语

每个原语都按 [kb-extending 的推导顺序](../../.knowledge/kb-extending.md#推导顺序)写：做法、上层做的代价、状态放在哪、事务和崩溃、模型和人怎样知道、怎样测试。

### 5.1 信件和发送者

做法：

- 输入 `userMessage` 改成 `letter`。信件带发送者、内容块、跳数和回信对象。
- 发送者有两种：
  - `user`：人，或者上层程序。CLI、bash 里运行的 `tau`、上层程序寄的信，都是用户的信。要标明来源，就在正文前加前缀，例如 `[Claude Code] `、`[后台任务] `。
  - `process`：另一个进程。只由库内工具和回信产生（5.3）。
- 头、合并、两种形状、张数上限和省略行、结束原因的文字：第 2 步已实现，细节和规则见 [kb-kernel](../../.knowledge/kb-kernel.md#信的头和合并)（[两种形状](../../.knowledge/kb-kernel.md#消息的两种形状)、[张数和省略行](../../.knowledge/kb-kernel.md#张数和省略行)、[结束原因的文字](../../.knowledge/kb-kernel.md#结束原因的文字)）。
- 还没实现的：
  - 每封信的张数在入口限制（5.6，第 6 步）。
  - `decide` 构造回信时（第 4 步），存进信件的 `ended` 已经按 `endedReason` 处理过。整页的报错不进收件人的信箱。
  - D25 三条说明的新措辞（5.3 规则 6，第 4 步）。

上层做的代价：做不到。信怎样写进工作段，只有 `decide` 能决定。

状态放在哪：`turn.queued` 存信件原样，写进段时才渲染。

事务和崩溃：和 v1 的用户消息一样。

测试：每种头；合并时用户的信加不加头；结束原因带换行、超长；裁剪；张数上限和占位行；两种发送者加入随机序列。

### 5.2 安全点投递

做法：

- 运行中到的信照旧进 `turn.queued`。
- **安全点**：当前这条助手消息的工具结果全部写完或补完、调用 `continueTurn` 之前。
- 到了安全点，按顺序做：
  1. 先查步数。`turn.steps` 已到 `STEPS_PER_TURN`，就按步数用完结束本轮，不合并。信留在 `queued`，由 `endTurn` 按 5.3 的规则 4、6 处理。这样发起这一轮的进程拿到的是最后一条助手消息的正文（可能为空），不会因为合并变成空串。
  2. `queued` 不空：经 5.1 的构造函数合并成一条用户消息写进段，按 5.3 的规则并入 `replyTo` 和 `hops`，清空 `queued`。
  3. 调用 `continueTurn`。
- 只有这一个安全点。换段成功以后、等模型回复时到的信，都等下一个安全点或者本轮结束。
- 本轮结束时 `queued` 还不空：由 `endTurn` 处理（5.3 的规则 5、6）。
- 写入不计步。下一次调用模型才计步。
- 用户在运行中用 `tau send` 发的信，因此在本轮里就被看到。连接仍等到本轮结束才收到最终回复。

坑点，写进 kb-kernel：

- 信在安全点并入以后，模型还没写出回复，这一轮就结束了：被停止、出错、`length`、工具调用太多、交接失败，或者交接以后步数用完。
- 这时最终回复是空串，寄信方收到正文为空的回信。
- 下一封信前面的 D25 说明会告诉模型这一点（5.3 规则 6）。

换段阈值的证明不变：

- 安全点写入的信在段末。交接请求不带段末的用户消息（[证明](../../.knowledge/kb-kernel.md#换段阈值)第 4 步）。
- 写入以后，`continueTurn` 照样先检查阈值。
- 换段时，这条信原样带到新段，张数按 5.1 限制。

上层做的代价：做不到。什么时候把信写进段，只有 `decide` 能决定。

状态放在哪：没有新状态。

事务和崩溃：在处理那条工具结果的事务里。

模型和人：模型在下一次调用时看到。

要核实：

- 工具结果后面紧跟一条用户消息，在用的每条模型路径都要接受。
- tau 在停止之后已经会产生这种形状。pi-ai 的 Anthropic 转换器会把它变成两条相邻的 `user`。
- 第 3 步按 5.7 的核实表核实在用的模型。结论只对核实过的模型成立：消息形状被不被接受由后端决定，路径相同、后端不同也要重核。

测试：纯函数层的随机序列；“带工具调用的助手消息后面紧跟它的结果”这条不变量照样成立；步数用完时不合并，回信的正文和不合并时一样。

### 5.3 进程之间：寄信、派生、停止、回信、跳数

库内工具（预设 `tools` 含 `agents` 时有）：

| 工具 | 参数 | 做什么 |
|---|---|---|
| `post` | `to`、`text`、`reply?` | 往 `to` 的信箱投一封信。`reply` 为真时，信带 `replyTo` = 自己 |
| `spawn` | `preset`、`text` | 读预设，建新进程（`parent` = 自己），第一封信带 `replyTo` = 自己 |
| `stop_process` | `process` | 往它的信箱放一个 `stop` |

- 工具说明要写明三件事：
  - 对方只在处理这封信的那一轮结束时回信一次，之后的几轮不回。
  - 对方在同一轮里处理了你的几封信时，只回一封。
  - 自己结束本轮去等别的事，等自己回信的进程会立刻收到这时的回复。

结果：

| 情形 | 结果 | `isError` |
|---|---|---|
| `post` 成功 | `已寄给 <id>。`；`reply` 为真时再加 `它处理这封信的那一轮结束时会给你回信，之后的几轮不会。` | 否 |
| `spawn` 成功 | `已建进程 <id>，预设 <preset>。它这一轮结束时会给你回信，之后的几轮不会。` | 否 |
| `stop_process` 成功 | `已给 <id> 发出停止。` | 否 |
| 收件人或目标不存在 | `没有进程 <id>。` | 是 |
| `post` 给自己 | `不能给自己寄信。` | 是 |
| `stop_process` 停自己 | `不能停止自己。要结束这一轮，直接回复，不再调用工具。` | 是 |
| 预设读不出；第 6 步起还有启动检查不通过，第 7 步起还有工具定义读不出 | `预设 <preset> 读不出：<原因>` | 是 |
| 跳数到上限 | `跳数到上限（32）：这封信是被进程之间的信一路引出来的。结束本轮，等用户的下一封信。` | 是 |
| 参数不对 | `参数错误：<说明>` | 是 |

停止：

- `stop` 结束目标此刻正在跑的这一轮。它不认是哪一轮：发出之前目标已经开了新一轮，停掉的就是新的那一轮。目标空闲时什么都不发生。
- 被停止的一轮照样寄回信。所以停一个子进程，会唤醒在等它的父进程。
- 要停一棵进程树：先停全部子孙，再停祖先，直到 `ps` 里都空闲。这不原子，只能尽力而为：
  - 被回信唤醒的祖先，在停止到达之前可能又建了新的子进程，要再停一遍。
  - 每个被回信唤醒的祖先，多一次被中止的模型调用。
  - 能运行命令的进程用 `tau start` 建的进程没有 `parent`，按 `parent` 找不到（第 12 节）。

回信：

- 回信的正文是这一轮的最终回复：从段尾往前，遇到用户消息之前的最后一条助手消息的正文。
- 这个算法已经在纯函数层（`finalReply`，见 [kb-kernel](../../.knowledge/kb-kernel.md#最终回复)）。服务的 `settle` 也调用这一份，但照 v1 在提交之后的段上算。所以停止时如果有排队的信，等着的连接拿到空串（和 v1 一样），回信拿到的是合并之前的最终回复。`decide` 构造回信是第 4 步。
- 回信由 `decide` 的 `out` 给出。存储层在同一个事务里把它放进收件人的信箱。
- 回信不带 `replyTo`。所以回信永远不会引出新的回信。
- “等子进程”不是一个状态：父进程结束本轮，回信到了，它就被唤醒。
- 回信只覆盖处理那封信的那一轮。进程为了等子进程或后台任务而结束本轮，等它回信的进程收到的就是这时的回复，例如“已派出”。之后几轮的结果不会自动寄上去。出路见[第 8 节](#8-上层建筑的做法)的“多 Agent：等待”。
- 子进程要问父进程，就在回复里提问、结束本轮。问题作为回信到父进程。父进程用 `post`（`reply` 为真）回答。

`replyTo` 和 `hops` 的规则：

1. 一封信写进段时，它的 `replyTo` 和 `hops` 才并进 `turn`：`replyTo` 加进集合，去重；`hops` 取最大。写进段的时机有三个：空闲时收信、安全点、`endTurn`。
2. 空闲时收信，开新一轮：新一轮的 `replyTo` 和 `hops` 只取自这封信。
3. `endTurn` 按这个顺序做：补工具结果；算最终回复；寄回信；处理 `queued`。
4. 寄回信：
   - `turn.replyTo` 里的每个进程，收一封回信，正文是最终回复，可能为空。
   - 结束原因不是 `done` 时，`queued` 里信的 `replyTo`、不在 `turn.replyTo` 里的进程，各收一封正文为空的回信。
   - 每个进程最多一封。头只写结束原因（5.1），不说信处理了没有。正文为空、结束原因又不是正常结束，寄信方就知道没拿到回答。要答案就再寄。
   - 这些回信的 `hops` 都是 `max(turn.hops, queued 里信的 hops) + 1`。
5. 处理 `queued`，结束原因是 `done`：合并写进段，开新一轮。新一轮的 `replyTo` 和 `hops` 只取自这批信，不继承上一轮。
6. 处理 `queued`，结束原因不是 `done`：合并写进段，进入 `idle`。这批信的头里仍写着“它在等回信”。下一封信前面的 D25 说明在它们之后，负责纠正：
   - 被停止：`（上一轮被停止。上面还没回复的消息都已取消：不要回应它们，只回应下面的信。）`
   - 步数用完：`（上一轮的步数用完了，停在中途。如果有进程在等你回信，它们已经收到上一轮的结束通知，之后的回复不会寄给它们。）`
   - 出错：`（上一轮出错，没有做完：<原因>。如果有进程在等你回信，……）`，后半句同上。
   - 安全点并入、随后这一轮异常结束的信（5.2 的坑点），也靠这几句纠正。
   - 措辞是暂定的。D25 的措辞用真模型量过，第 4 步照 D25 的办法重量。要不要再让模型放下上一轮末尾合并进来的信，重量时一起定。

跳数：

- 用户的信，`hops` 为 0。
- `post`、`spawn` 寄出的信，`hops` = `turn.hops + 1`。回信见规则 4。
- `post` 和 `spawn` 寄出的信，`hops` 超过 `HOPS_MAX`（32）时失败。回信不受这个限制。
- 跳数只保证进程之间的信不会无限循环，不限制花费：每一跳都可以扇出（第 12 节）。
- 跳数只管库内的 `post`、`spawn` 和回信。从 bash 寄的信都是用户的信，`hops` 为 0。所以跳数是防失控的保险，不是边界。
- 跳数也限制了顺序委派的次数：每派出一个子进程、收一封回信，`turn.hops` 加 2。子进程不再委派时，第 k 次寄出的信跳数是 2k − 1。所以一封用户的信引出的顺序委派最多 16 次，第 17 次是 33，超过上限。每多一层嵌套，约减半。安全点并入的旧回信，也会把用户新开的一轮的跳数抬高。真不够用时放宽 `HOPS_MAX`，放宽它不算改契约（第 10 节）。

环境变量：

- bash 和工具定义（5.5）运行的命令，拿到 `TAU_PROCESS`（进程 ID）和 `TAU_PIPE`（服务实际监听的管道名）。
- CLI 连接服务时，`TAU_PIPE` 有值就用它，否则用默认的管道。这样测试服务里的 Agent 运行 `tau`，不会连到正式服务上。
- 测试要清掉从外面继承来的 `TAU_` 变量。

上层做的代价：

- 不原子。用工具定义运行 `tau send`、`tau start`、`tau stop`，也能寄信、建进程、停进程。但它们是库外工具：在做完和写结果之间崩溃，模型看到“被中断”，再做一次。信就重复，子进程就多一个，停止就可能停掉对方后来的一轮。重做有害，所以不按第 2 节第 4 条第 2 支放上层。
- 丢数据。回信要和一轮的结束在同一个事务里寄出。上层只能盯着 `watch`，它没在运行时，回信就漏了。

状态放在哪：

- `replyTo` 和 `hops` 在 `turn` 里。它们只在运行中有意义。
- `parent` 在进程记录里，建好后不变。
- 寄出的信和停止，在收件人的信箱里。

事务和崩溃：

- 三个库内工具都在处理输入的事务里执行，和工具结果一起提交。崩溃时要么都发生，要么都没发生。
- 库内工具永不抛错。抛错会让事务回滚，这条输入留在信箱队头，所有进程都卡住（[kb-store 的坑点](../../.knowledge/kb-store.md#坑点)）。所有失败都变成 `isError` 的结果。
- `post` 和 `stop_process` 读收件人的进程记录，查它存不存在。
- `spawn`：
  - 不调用 `startProcess`，因为事务不能嵌套。它用 `start` 建记录，插入进程行，再把第一封信放进新进程的信箱。
  - `start` 的 `Env` 按子进程的预设算：记忆视图是子进程的，不是父进程的。
  - 新 ID 由父进程 ID、这次调用的副作用编号和尝试次数算出，例如取 sha256 的前 8 个十六进制字符。撞上已有的 ID，就把尝试次数加一再算。这样崩溃注入测试的重放是确定的，撞 ID 的测试也好写。
  - 读预设和工具定义，用服务传给 `handleNext` 的读取函数。测试传假的。
  - 冻结快照时做启动检查（5.6，第 6 步起）。读不出或者不通过，就是错误结果，什么都不建。
- 两处规则的例外，要写进决策记录：
  - “库内工具只碰库”：`spawn` 还读预设文件和工具定义文件，查工作目录。
  - “处理一条输入只读进程记录和当前工作段”：`post`、`stop_process` 读收件人的记录，`spawn` 读文件。

模型和人：

- 寄信方从工具结果知道寄出了。收信方看到带头的信，从头知道要不要回信。
- 投影和 `self`：每个进程带 `parent`；运行中的子进程各一行，空闲的只给个数。空闲子进程的 ID，从协议 `ps` 的投影里按 `parent` 找（第 8 节“列出会话”）。

测试：

- A 问 B，B 回信。B 被停止时，回信写“被停止”。
- B 这一轮结束时，排队的信里也有要回信的：`done` 时开新一轮，带上它们的 `replyTo`；不是 `done` 时寄正文为空的回信。同一个进程只收一封。
- 最终回复在合并排队的信之前算。
- 在寄信、派生、停止的事务前后杀服务。
- 两个互相寄信的进程在 `HOPS_MAX` 处停住。顺序委派（子进程不再委派，每次等到回信再派下一个）：前 16 次 `spawn` 成功，第 17 次报跳数到上限。
- `spawn` 的 ID 撞上已有的；子进程的记忆视图；预设读不出；启动检查不通过（第 6 步补）。
- 收件人不存在；给自己寄信；停自己。

### 5.4 主动换段

做法：

- 库内工具 `handoff`，没有参数，总是有，和 `self` 一样。
- 结果是 `将在这批工具结果之后换段。`，`isError` 为假。
- 到了安全点，`continueTurn` 发现最后一条助手消息里有 `handoff` 调用、并且它的结果不是错误，就进入 `awaitingModel(handoff)`，不看阈值。
- 补的结果（`INTERRUPTED`、`SKIPPED`）都是错误。所以没执行的 `handoff` 不会触发换段。
- 交接失败以后，下一封信一来又会立即换段。这和到阈值时一样，是有意的。

上层做的代价：做不到。换段只能由 `decide` 发起。

状态放在哪：不存。从工作段的最后一条助手消息和它的结果算出来。

纯函数层的不变量（kb-kernel 的“不变量”一节，`awaitingModel` 一行）改一句：`purpose` 是 `handoff`，当且仅当用量到阈值，或者最后一条助手消息里有成功的 `handoff` 调用。

测试：纯函数层的单元测试；和阈值同时成立；和安全点投递同时发生；被补成“未执行”的 `handoff` 不触发。

### 5.5 工具定义

“工具定义”专指 `~/.tau/tools/` 下的文件。请求里给模型看的工具名、说明和参数，叫“工具描述”（第 7 节第 0 步统一用词）。

格式：

- 工具定义是文件：`~/.tau/tools/<name>.json`。

```json
{
  "description": "……",
  "parameters": { "type": "object", "properties": { }, "additionalProperties": false },
  "command": "node E:/tau/extras/notes/notes.mjs write",
  "timeout": 120,
  "output": "text"
}
```

- 名字匹配 `^[A-Za-z0-9_-]{1,64}$`，按目录项精确匹配，和预设一样。
- 名字不能和内置工具重名（`read`、`write`、`edit`、`bash`、`self`、`handoff`、`post`、`spawn`、`stop_process`、`memory_get`、`memory_set`、`memory_delete`），也不能和工具组重名（`memory`、`agents`）。
- `description` 必填，是字符串。
- `parameters` 必填，是 `type` 为 `object` 的 JSON Schema。
  - 只查顶层。顶层不是 `object` 时，有的 provider 会拒绝每一次请求。
  - 内层不查，pi-ai 也不查，原样转发。内层写错时，进程第一次调用模型就失败。出路见风险表。
- `command` 必填，是字符串。
- `timeout` 可选，是 1 到 600 的整数，单位秒，默认 120。
- `output` 可选，是 `text` 或 `content`，默认 `text`。
- 有别的字段就报错，和预设一样。
- 预设的 `tools` 可以写这些名字。文件读不出、格式不对、重名、超过大小上限：启动失败。`spawn` 时是错误结果。
- 大小上限：
  - 一个定义的大小，是 `JSON.stringify({ description, parameters })` 的 UTF-8 字节数，不超过 `TOOL_DEF_MAX_BYTES`（暂定 16 KiB）。
  - 一个预设用到的全部定义，按冻结进快照的整个 `ToolDef` 算，含 `name`、`command` 和补上的默认值。各自 `JSON.stringify` 的 UTF-8 字节数相加，不超过 `TOOL_DEFS_MAX_BYTES`（暂定 64 KiB）。
  - 原因：定义冻结进 `state_json`，每条输入整行重写，`self` 和 `ps` 也要解析它。定义还占每次请求的上下文，启动检查要算上它（5.6）。
- 启动进程时，用到的定义冻结进预设快照。之后改文件，只影响新启动的进程。
- 工具描述里，工具定义排在内置工具之后，按预设 `tools` 里的顺序。
- 参数先按 schema 校验（pi-ai 的 `validateToolArguments`），和内置工具一样。

运行（整节是契约，第 10 节）：

- 工具定义都是库外工具，由执行器运行。
- 它走 bash 的整套机制：用 bash 运行 `command`，工作目录、超时、中止、结束进程树、输出上限、环境变量（5.3）都一样。
- 参数的 JSON 从标准输入给，写完就关。
- 命令不读标准输入就退出时，写入会报 `EPIPE`，要忽略它。标准输入的流上要有错误监听器，否则 Node 会按未捕获异常让服务退出。
- bash 工具不给标准输入，照旧是空设备。
- `output: text`：和 bash 一样。标准输出和标准错误合在一起是结果。退出码不是 0 就是错误。
- `output: content`：
  - 标准输出和标准错误分开收。
  - 退出码不是 0：结果是错误，文字和 `text` 时一样。
  - 退出码是 0：丢掉标准错误。标准输出必须是一个 JSON 数组，每项是 `{ "type": "text", "text": … }` 或 `{ "type": "image", "path": … }`。
  - 先解析 JSON，检查每一项的格式和图片的张数（不超过 `IMAGES_PER_MESSAGE`），再读图片文件。读之前先看大小，超过 `IMAGE_MAX_BYTES` 就不读。
  - `path` 只认 Windows 的绝对路径：盘符开头或 UNC。msys 的 `/tmp/x.png` 不认，和预设的 `workdir` 一样。
  - 文本项按顺序用换行连起来，成为结果的文本块。图片按 5.6 检查，存进 `blobs`。
  - 不合法时，结果是错误：`content 输出不合法：<说明>`。不合法包括：标准输出超过上限被截断、不是合法 JSON、不是数组、项的格式不对、图片超过张数、`path` 不是 Windows 的绝对路径、文件读不出、图片不合格（5.6）。
- MCP 不进内核（第 6 节）。

上层做的代价：做不到。模型能调用哪些工具，只由内核给的工具描述决定。没有工具定义，上层的功能只能让模型自己拼 bash 命令：没有参数说明，没有 bash 的预设也用不了。

状态放在哪：预设快照里。

事务和崩溃：和 bash 一样。被中断就报“被中断”，不重做。带图的 `content` 结果，图片在执行器上报结果的事务里插入 `blobs`（5.6）。

测试：用假的命令测：参数从标准输入来、命令不读标准输入、退出码、超时、中止、输出上限、`content` 输出的每种不合法；快照冻结；格式、名字、重名和大小上限。

### 5.6 内容块和图片

入口：

- 图片只从两个入口进来：协议的 `start`、`send`；工具定义的 `content` 输出。
- 入口按顺序检查，不合格就拒绝。协议回 `error`，工具定义的结果是错误。这些条件是契约（第 10 节）。
  1. 张数：一个请求、一次 `content` 输出，最多 `IMAGES_PER_MESSAGE`（暂定 2）张。
  2. 大小：每张不超过 `IMAGE_MAX_BYTES`（暂定 1.5 MiB）。
  3. 类型：按文件头的魔数判断，只收 png、jpeg、gif、webp。不信声明的类型和扩展名。
  4. 尺寸：宽和高都不超过 `IMAGE_MAX_EDGE`（暂定 2000 像素）。
     - 尺寸从文件头读：PNG 的 IHDR、GIF 的逻辑屏幕描述、WebP 的 VP8、VP8L、VP8X 块，都在开头固定的位置。
     - JPEG 要从头逐段跳过标记段（APPn、EXIF 等），找到 SOFn，包括渐进式的 SOF2。
     - 不需要新依赖。
- 为什么入口要查：不合格的图片进了段，每次调用模型都会失败，连交接调用也失败，进程就永远卡住。例如 Anthropic 拒绝边长超过 8000 像素的图。2000 像素和 pi-ai 模型目录给每个收图片的模型定的缩放尺寸一样。截图类的工具定义要自己先缩小。
- 目标进程的模型不收图片（快照的 `input` 里没有 `image`）：入口照样先按顺序检查，不合格就拒绝。都合格，才把每张图换成一行 `[图片：模型不支持，已省略]`，不存图片。所以这种进程的段里永远没有图片。
- 文件头完好、数据损坏的图片仍可能进段。出路见风险表。

存储：

- 新表 `blobs(hash TEXT PRIMARY KEY, data BLOB NOT NULL) STRICT`。`data` 是原始字节。
- `hash` 是原始字节的 sha256，64 位小写十六进制。
- 工作段里，图片块的 `data` 写成 `blob:<hash>`，`mimeType` 是入口按魔数算出的类型。
- 类型不另存。`blob` 请求的回复要类型时，用入口那个魔数函数现算。这是同一个纯函数，不是第二个来源。
- `blobs` 的插入，和引用它的信件或工具结果在同一个事务里：协议请求的事务，或者执行器上报结果的事务。
- 只增不删，和旧段一样。
- 纯函数层里不出现图片的字节。`buildContext` 照样返回引用，执行器调用模型之前换成真数据。

请求里的图片：

- 一次请求最多带段里最近的 `IMAGES_PER_REQUEST`（记作 K，暂定 8）张。
- 段里有 n 张：n 不超过 K 时全带。否则从最早的起整批省略，每批 B 张（暂定 4），省到剩下不超过 K 张为止，也就是省略 B × ⌈(n − K) / B⌉ 张。请求里留最近的 K − B + 1 到 K 张。省略的图换成一行 `[图片：较早的图片，已省略]`。
- 现在 K = 8、B = 4：n = 9 到 12 省 4 张，n = 13 到 16 省 8 张。省略的张数每来 B 张图变一次。成批省略是为了提示缓存：请求的前缀不是每来一张图都变。
- 这由 `buildContext` 做，是段的纯函数，不改库。
- 所以一次请求里图片的数据不超过 8 × 1.5 MiB × 4/3 = 16 MiB。这低于 Anthropic 每次请求 32 MB 的上限，文字不超过约 4 MiB 时也低于 Google 的 20 MiB。
- 这是“换段是唯一缩短上下文的办法”的例外，也改变了旧消息在请求里的样子。要写进决策记录。理由：截图常常一步一张，按张数换段会每几步就换一次段。

用量估算和换段阈值：

- 段里只有收图片的预设才会有图片。每张图按 `IMAGE_TOKENS`（暂定 5000）算，不看字节：`messageBytes` 把一张图算成 `IMAGE_TOKENS × BYTES_PER_TOKEN` 字节。
- 锚点是真实用量，已经包括请求里真的图片。锚点之后的图片按上一条估算。
- R 是快照的纯函数，`handoffThreshold` 照样只看快照：
  - 不收图片的预设：R = `tokens(MESSAGE_MAX_BYTES)` = 16,384，和 v1 一样，阈值也不变。
  - 收图片的预设：R = 16,384 + `IMAGES_PER_MESSAGE × IMAGE_TOKENS` = 26,384。
- [阈值公式和证明](../../.knowledge/kb-kernel.md#换段阈值)照原样代入 R。
- 证明的前提多一条：`IMAGE_TOKENS` 不低于在用模型一张图的真实 token 数。图按入口允许的各种形状算，不只正方形。
- 按各家文档粗算，一张 2000 像素的图：
  - Anthropic 从 Opus 4.7 起的模型（含 claude-opus-5-5）最多约 4,784；更早的（含 claude-haiku-4-5）先缩到长边 1568，约 1,600。
  - Gemini 按 768 像素分块，约 2,322。
  - OpenAI 高细节按 512 像素分块，2000 × 768 约 1,445，比 2000 × 2000 的 765 还多。
  - DeepSeek、MiMo、Muse 的算法不知道，要实测。
- 收图片的预设的新阈值（按 `IMAGE_TOKENS` = 5000 算）：

| W | 旧 T | 新 T |
|---|---|---|
| 64,000 | 27,520（43.0%） | 17,520（27.4%） |
| 128,000 | 75,520（59.0%） | 65,520（51.2%） |
| 200,000 | 129,520（64.8%） | 119,520（59.8%） |
| 1,000,000 | 729,520（73.0%） | 719,520（72.0%） |

- 64K 窗口收图片时，阈值只有 17,520。带图的信赶上换段时，新段的第一条可能已经超过阈值，于是再换一次段。这一次，信的原文和图被概括进交接说明，图从此丢失。这条写进 kb-kernel 的坑点。

量 `IMAGE_TOKENS`（第 6 步）：

- 形状：2000 × 2000、2000 × 1000、2000 × 768。按块计价的模型，最坏的不一定是正方形。
- 模型：在用、收图片、能调到的每个模型。现在是 opencode-go 的 deepseek-v4.1-flash、mimo-v2.6-flash（openai-completions），gpt-6-luna、muse-spark-1.3-contributor（openai-responses），加上 anthropic/claude-haiku-4-5。
- claude-opus-5-5 不实测，用文档的上限 4,784。Anthropic 的凭据只许配 Haiku 用，这是用户的限制。要实测，先问用户。
- 量法照 D24：同一个请求带图和不带图，比 `input + cacheRead + cacheWrite` 的差。
- 同时核实这些模型真的收图片，四种类型各发一张，含一张动图 GIF。目录写着收、接口却拒绝的模型或类型，图片进段以后每次调用都失败。遇到这种情况，冻结之前定对策，写进决策记录。
- `IMAGE_TOKENS` 取全部测量值、文档上限和 5000 里的最大值，向上取整。
- 决策记录写明量过哪些模型。以后收图片的预设换成没量过的模型，先量。这条写进 kb-kernel 的坑点。

启动检查：

- `start` 和 `spawn` 冻结快照时检查：

  `tokens(固定部分) + 记忆的上界 < handoffThreshold(快照)`

  - 固定部分：预设提示词、工作目录那一行、`JSON.stringify(工具描述)`。工具描述含内置工具和工具定义，口径和 `contextUsed` 一样。
  - 记忆的上界：预设含 `memory` 时，是 `MEMORY_VIEW_MAX_BYTES` 的 token 数加上记忆的标题；否则是 0。
  - 不通过就启动失败，报出固定部分、记忆的上界和阈值各多少 token。
- 为什么要查：
  - 证明的前提是“系统提示词和工具描述本身远小于窗口”。v1 不检查，是 D22 按 YAGNI 定的：换段循环由 `stepLimit` 收住。v1 的预设提示词其实也没有大小上限。v2 的工具定义最多 64 KiB，固定部分更容易到阈值，所以要查。
  - 固定部分加记忆到了阈值，每个新段一开头就到阈值。没有启动检查，这种进程每封信都交接一次，再在下面的检查上出错，什么都做不了。启动时就挡住，用户马上知道。
  - 这个式子等价于 F + M + R + `MARGIN_TOKENS` + 2·OUT < W。它比“交接请求放得进窗口”（F + M + R + `MARGIN_TOKENS` + OUT ≤ W）更严，所以交接请求一定放得进窗口。
  - 阈值不大于 0 的小窗口，也被它挡住。
- 它只挡固定部分加记忆到阈值的预设。差得不远的，新段的第一条（交接头加说明）还会把新段推到阈值。这一种由下面的检查兜住。

交接以后的检查：

- `onHandoff` 接受交接回复（`stop` 或 `length`，说明不空）以后、建新段之前，查一次假想的新段：记忆视图取 `env` 里的当前视图，段里只有一条 `clip(HANDOFF_HEADER + 交接说明)`，不带要带过去的信。
- 判断和 `continueTurn` 用同一个：`contextUsed ≥ handoffThreshold`。不另写算式。所以检查通过时，不带信的新段一定低于阈值。
- 到阈值，就按交接失败结束本轮：不写交接回复，不建新段。排队的信照 `endTurn` 合并写进旧段，和别的交接失败一样。
- 原因写成：`交接失败：新段一开头就到阈值（固定部分 <f>、记忆 <m>、交接说明 <n>，共 <x> / <T> token）`。x 用上面的判断算，n 取 x − f − m。
- 这样每封信最多浪费一次交接调用，不会空转到 `stepLimit`。
- 带过去的信让新段到阈值时，检查不拦，照常再换一次段（上面 64K 收图片的情形）。

上层做的代价：做不到。上层没有办法把图片放进模型的上下文。

状态放在哪：`blobs` 表。引用在工作段里。

事务和崩溃：

- 图片和引用它的信件或工具结果一起提交。
- 可能有没人引用的图片：带图的工具结果进了信箱，又因为过时被丢掉。图片按内容寻址、只增不删，这样的图片无害。
- 存储层不变量加一条：信箱、`turn.queued` 和段里的每个 blob 引用，`blobs` 里都有对应的行。它由 `assertStoreInvariants`（`test/store/invariants.ts`）检查，崩溃注入测试每一步之后照常调用。
- 带引用的只有协议的信和工具结果。`post`、`spawn` 和回信只有文本。

测试：张数；大小；魔数和四种类型；尺寸（每种格式，包括带 EXIF 的 JPEG）；不收图片的模型先检查、再换成占位行；引用完整性；执行器替换数据；请求里的成批省略（n = 8、9、12、13）；用量估算；两种 R；启动检查挡住固定部分加记忆到阈值的预设；交接以后的检查（固定部分离阈值不到一份说明时，每封信只交接一次就出错；带过去的信让新段到阈值时不拦）；最坏的图片负载下交接请求放得进窗口。`test/kernel/acceptance.test.ts` 里“每段一开始就超过阈值”的用例，改成交接一次就以交接失败结束。

### 5.7 调用模型：思考级别和重试

思考级别：

- 预设加可选的 `thinking`，值是 pi-ai 的思考级别：`minimal`、`low`、`medium`、`high`、`xhigh`、`max`。快照冻结它。
- 执行器按它传 `reasoning`。不写就不传，由 pi-ai 按模型的默认处理。不同模型的默认不一样：有的不思考，有的按 provider 的默认思考。
- 一次回复的总输出（含思考）不能超过 `outputMax`，这是换段阈值的前提。做法：
  - `cap = min(model.maxTokens, outputMax)`，和 v1 一样。
  - 调用时传 `{ ...model, maxTokens: cap }`，`options.maxTokens` 也传 `cap`。不传 `thinkingBudgets`，用 pi-ai 的默认预算。
  - 按预算思考的路径（anthropic-messages 上没有 `forceAdaptiveThinking` 的模型）：pi-ai 把预算加到 `maxTokens` 上，再按模型的 `maxTokens` 截。模型的 `maxTokens` 已经换成 `cap`，所以总数不超过 `cap`。
  - 其余路径（自适应思考、openai-completions、openai-responses 等）：思考和回答共用 `max_tokens`，就是 `cap`。这是 provider 的语义，第 3 步实测。
  - `xhigh` 和 `max` 在预算路径上按 `high` 的预算算（pi-ai 的 `clampReasoning`）。
- 为什么不从 `maxTokens` 里减预算：只有预算路径会把预算加回去。别的路径上，减掉的部分白白少了。窗口小的模型只剩 1,024，回复以 `length` 结束，本轮出错。
- 预算路径上回答的空间：
  - 回答最坏剩 max(`cap` − 预算, 1,024)。`cap` 不大于“预算 + 1,024”时，pi-ai 把预算压到 `cap − 1024`，回答只剩 1,024。
  - pi-ai 的默认预算：`minimal` 1,024，`low` 2,048，`medium` 8,192，`high` 及以上 16,384。所以回答只剩 1,024 的边界是：`high` 及以上 `cap` ≤ 17,408，`medium` ≤ 9,216，`low` ≤ 3,072，`minimal` ≤ 2,048。
  - pi-ai 1.0.0 的目录里，落在这里的是 vercel-ai-gateway 经 anthropic-messages 接入的 21 个非 Anthropic 模型，例如 zai/glm-4.5。其中 6 个连 `medium` 也落在范围里（`cap` 5,120 到 8,250）。Anthropic 自己的模型 `cap` 都不小于 25,000。在用的 haiku-4-5 在 `high` 及以上最坏剩 8,616。
  - 预设换到走预算路径的模型，先按上面的式子算。落在范围里，就把 `thinking` 降到不落在范围里的级别，或者不设 `thinking`，或者换模型。预设没有 `thinkingBudgets`，执行器也不传它。核实表查不出这件事，只能靠算。
- 思考块照 v1 写进段，按字节算进用量。

核实（第 3 步）：按 pi-ai 的路径分，每条路径核实在用的模型。查两件事：安全点之后的消息形状被接受（5.2）；请求体里的输出上限不超过 `cap`。

| 路径 | 模型 | 怎么核实 |
|---|---|---|
| anthropic-messages，按预算思考 | anthropic/claude-haiku-4-5 | 真调用 |
| anthropic-messages，自适应思考，effort 经插入的 system 消息传 | anthropic/claude-opus-5-5 | 只用 `onPayload` 和假的 `fetch` 断言请求体。真调用要先问用户 |
| openai-completions，deepseek 格式（发 `thinking` 字段） | opencode-go/deepseek-v4.1-flash | 真调用 |
| openai-completions，openai 格式（只发 `reasoning_effort`） | opencode-go/mimo-v2.6-flash | 真调用，设上 `thinking` |
| openai-responses | opencode-go 上在用的模型，例如 muse-spark-1.3-contributor | 真调用 |

- openai 兼容的三行再查一件事：思考算不算进 `max_tokens`。
  - 直接调 pi-ai，思考开到最高，`maxTokens` 设小（例如 1,024），问一个要想很久、答案很短的问题。
  - `usage.output` 超过 `maxTokens`：这条路径的 `outputMax` 前提不成立，不支持。
  - 没超过时，要同时满足两条，结论才算数：回复以 `length` 结束；真的思考过（有思考块，或者 `usage.reasoning` 大于 0）。不满足就换个更难的问题，或者调小 `maxTokens`，再测。看不出思考过，算没核实。
  - 只以 `length` 结束不算通过：思考不算进上限时，回答写满上限也以 `length` 结束。
- anthropic 的两行不用查这一件：Anthropic 的文档规定 `max_tokens` 含思考。这只对 Anthropic 自己的服务成立，别的后端走这两条路径，也要查。
- Anthropic 的凭据只许配 Haiku 用，这是用户的限制。
- openai-codex-responses 的请求不发输出上限，总输出可能超过 `outputMax`。tau 本来也调不了它：它只有 OAuth（D23）。不支持。
- 结论只对核实过的模型成立。消息形状和输出上限的语义由后端决定，路径相同、后端不同也要重核。预设换到没核实过的模型，先真调用核实一次。只有用户没许真调用的模型（现在是 claude-opus-5-5），才只断言请求体。

重试：

- 执行器调用模型时，传 `maxRetries` = `MODEL_RETRIES`（暂定 5）。
- pi-ai 只重试拿到成功的响应之前的失败：没有状态码的连接错误，以及 408、409、429 和 5xx 的错误响应，以错误响应的 `x-should-retry` 头为准。重试可以被中止。
- 等多久：
  - 错误响应带 `retry-after-ms` 或 `retry-after` 时，按它等。超过 60 秒就直接失败。429 通常带这个头，5 次最坏约 5 分钟。
  - 不带时，退避从 0.5 秒起翻倍，乘 0.75 到 1 的随机数，单次最多 8 秒。5 次一共约 12 到 16 秒，和 Pi SDK 默认的 3 次（2、4、8 秒）差不多。
  - 等的时候，进程停在“等模型”。
- 这不是重做副作用：还是同一个副作用，也还没有任何结果。崩溃后照样报“被中断”，不重做。
- 流式输出开始以后出的错不重试，本轮出错结束（风险表）。
- AGENTS.md 的“执行器……也不重试”要改成：执行器自己不重试；模型请求在拿到成功的响应之前的重试，交给 pi-ai。

需求来源：

- 本机 Pi Web 的 17 个角色里，16 个开着思考：max 8 个、xhigh 3 个、high 3 个、medium 1 个、low 1 个。
- Pi SDK 默认开着重试，最多 3 次，Pi Web 没有关。

上层做的代价：

- 思考级别：做不到。它是调用模型的参数。
- 重试：丢数据。上层只能等这一轮出错结束，再寄“继续”。这时回信已经寄出，新的一轮没有 `replyTo`，等回信的父进程拿不到结果。上层没在运行时也不会重试。

状态放在哪：思考级别在快照里。重试不存状态。

测试：执行器传给 pi-ai 的参数（用假的 pi-ai）；用 `onPayload` 和假的 `fetch`，对每条在用的路径断言请求体里的输出上限不超过 `cap`，预算路径上预算小于 `max_tokens`；第 3 步的真模型核实。

### 5.8 累计用量

做法：

- 进程记录的 `usage` 累计输入、输出、缓存读、缓存写四个 token 数，已实现，规则见 [kb-kernel](../../.knowledge/kb-kernel.md#累计用量)。
- 不存钱数。Pi Web 只显示 token。pi-ai 按单次请求的输入量分档计价，钱数从累计的 token 数算不出来。

上层做的代价：丢数据。交接回复和没写进段的回复，用量哪里都没存，上层从段里算不全。上层盯着 `watch` 累加，它没在运行时就漏了。

状态放在哪：进程记录。它跨段累计，从工作段算不出来（[kb-extending 原则 3](../../.knowledge/kb-extending.md#核心原则)）。

模型和人：投影和 `self` 多一行累计用量。人用上层的命令行看（第 8 节）。

测试：每种回复都累加；重复的结果、编号对不上的结果不加。

### 5.9 协议

分帧：

- 管道名是 `\\.\pipe\tau`。CLI 有 `TAU_PIPE` 时用它（5.3）。
- 一个连接一行请求。服务回若干行，每行一个 JSON，以 `\n` 结束。
- 回完由服务关闭连接。`watch` 例外：由客户端断开。
- 客户端发完请求，不能半关闭（不调用 `end` 或 `shutdown`）。
  - Windows 命名管道不支持半关闭：客户端一半关，连接就整个关了，之后服务写的都丢。两端都设 `allowHalfOpen` 也一样。
  - 同步写出的回执、快照和 `history` 能到，后来的最终回复和 `watch` 的增量都丢。所以简单的测试发现不了。
  - 这条写进 kb-service 的坑点。
- 客户端可以在回执之后直接断开（`destroy`）：服务照常处理，不再给它写。v1 已经这样处理 `tau send` 被 Ctrl+C 的情形。

v2 的请求和回复（`src/protocol.ts`）：

```ts
type Request =
  | { op: "start"; preset: string; text: string; images?: string[] }   // images 是 base64
  | { op: "send"; process: string; text: string; images?: string[] }
  | { op: "stop"; process: string }
  | { op: "ps" }
  | { op: "history"; process: string; segment?: number; from?: number }
  | { op: "blob"; hash: string }
  | { op: "watch"; process?: string };

type Reply =
  | { type: "receipt"; process: string }
  | { type: "text"; process: string; n: number; delta: string }        // v1 只有 delta
  | { type: "final"; reply: string; ended: Ended | null }
  | { type: "ps"; processes: Projection[] }
  | { type: "message"; segment: number; seq: number; message: Message }
  | { type: "end"; segment: number; messages: number }                 // history 读完
  | { type: "blob"; mimeType: string; data: string }                   // data 是 base64
  | { type: "update"; self: Projection["self"] }
  | { type: "error"; message: string };
```

请求：

| 请求 | 做什么 | 回复 |
|---|---|---|
| `start`、`send` | 同 v1，可以带图片（5.6 的入口检查） | 同 v1 |
| `stop`、`ps` | 同 v1。投影是第 4 节的 v2 投影 | 同 v1 |
| `history` | 读一段的消息，从段内序号 `from` 起。段默认是当前段，`from` 默认是 0 | 每条一行 `message`，最后一行 `end`，然后关闭 |
| `blob` | 读一张图片。`hash` 不带 `blob:` 前缀 | 一行 `blob`，然后关闭。`hash` 不存在回 `error` |
| `watch` | 订阅变化 | 一直推送，直到客户端断开 |

- 没有单独的“寄信不等回复”的请求。它就是 `send` 收到回执后断开。

`history`：

- 每行带段号和段内序号。
- 读完发一行 `end`：段号和这一段的消息条数。客户端从它知道读完了、读的是哪一段、段尾在哪。没收到 `end` 连接就关了，就是没读完。
- 进程不存在、段号越界，回 `error`。`from` 超过段尾时只发 `end`。
- 每行的 `message` 是 pi-ai 1.0.0 的消息 JSON，图片的 `data` 是 `blob:<hash>`。这个格式是契约。升级 pi-ai 时消息 JSON 有变化，算契约变更。
- 客户端看到投影里的消息条数变了，就用 `from` 读新增的部分。

`watch`：

- 订阅时先推一次快照：带 `process` 时推它的 `update`，不带时推每个进程的 `update`。之后只推增量，所以先 `ps` 再 `watch` 也不会漏。
- 之后每次 `handleNext` 处理了某个进程的输入，就给订阅它的连接推这个进程的 `update`。
  - `update` 只有 `self` 部分，不带兄弟和子进程。
  - 它由 `handleNext` 返回的新记录和新段算出，不再读库。
- 流式文本照样推，带进程 ID 和副作用编号。客户端用编号丢掉过时的文本。
- 不推“最终回复”。客户端看到进程回到 `idle`，自己用 `history` 读。
- 订阅表和 `start`、`send` 的观察者表分开。`settle` 不变。
- 写缓冲有上限，推完快照就开始查：
  - 推完快照时，记下连接的 `writableLength`，记作 S。之后 `writableLength` 超过 S + `WATCH_BUFFER_MAX`（暂定 1 MiB），就断开这个订阅。
  - `writableLength` 对字符串按字符计，不按字节。上限也按它的单位算，不另算字节。
  - 快照先写先排出，所以推完快照时不会误断。内存有上界。
  - 不能等快照排空再查：订阅方一直不读、快照又大于管道的缓冲时，快照永远排不空，上限就永远不生效。
- 订阅不存在的进程，回 `error`。
- 服务正常退出时，先断开所有 `watch` 连接，再等别的连接结束。退出开始以后才读到的 `watch` 请求，回 `error` 并关闭。

CLI：

- 命令、输出和退出码都照 v1：`serve`、`start`、`send`、`stop`、`ps`。v2 只加一条：连接服务时，`TAU_PIPE` 有值就用它（5.3）。
- 读历史、寄信不等回复、带图片、看父进程和累计用量，都放上层的命令行做（第 8 节）。它们只是协议的薄封装，上层做没有代价（第 2 节第 3 条）。这样冻结的 CLI 也小。
- 仓库根目录加一个不带扩展名的 `tau` 脚本，和 `tau.cmd` 放在一起。它和 `tau.cmd` 一样是启动脚本，不是功能：

```sh
#!/bin/sh
MSYS_NO_PATHCONV=1 exec node "$(cygpath -w "$(dirname "$0")")/src/main.ts" "$@"
```

  - 为什么要它：bash 找不到不带扩展名的 `tau`。`tau.cmd` 能运行，但要写全名，还经 cmd.exe 解析参数。
  - `MSYS_NO_PATHCONV=1`：不让 msys 改写参数。否则以 `/` 开头的正文会被改成 Windows 路径。
  - `cygpath -w`：node 要 Windows 路径才找得到 `main.ts`。
  - 这个变量只为 `exec node` 这一步而设，却会留在 node 的环境里。在 Git Bash 里运行 `tau serve`，服务就带着它，bash 工具的每条命令都不再转换路径。所以 bash 工具构造子进程环境时去掉它，和加 `TAU_PROCESS`、`TAU_PIPE` 在同一处（`src/tools/bash.ts`）。工具定义走同一套机制，自动覆盖。
- `tau.cmd` 经 cmd.exe 解析参数，正文里的 `&` 会被当成命令分隔符。外部程序和系统计划任务寄信，要直接连管道，或者直接运行 `node <仓库>\src\main.ts`，不要经 `tau.cmd`。这条写进 kb-service 的坑点。

上层做的代价：

- 做不到。上层只能通过协议看内核：读不了历史，就做不了历史检索；拿不到流式文本，页面就看不到实时输出。
- 慢。没有 `watch`，上层只能反复 `ps`。`ps` 读全部进程，随年头变慢。

事务和崩溃：和 v1 一样。回执在提交之后才发。读的请求不开写事务。

测试：每个新请求的成功和失败；`history` 的 `from`、越界、`end` 行；`watch` 的快照、增量、断开后不再推送、写缓冲上限（含一直不读、快照大于管道缓冲的订阅）、服务退出时断开、退出时才到的 `watch`；CLI 经 `TAU_PIPE` 连测试服务；`bash()` 在环境带 `MSYS_NO_PATHCONV` 时，命令看不到它，msys 路径照常转换。

## 6. v2 也不做的

按第 2 节第 2 条，现在不做、也不进内核的（本机没用过，或者 tau 不需要）：

| 不做 | 为什么 | 要的话上层怎么做，代价是什么 |
|---|---|---|
| 延时投递、定时器 | 本机没用过：Pi Web 没有定时器 | 系统计划任务到点直接运行 `node <仓库>\src\main.ts send <进程> <正文>`，或者经 Git Bash 运行 `bash -c 'tau send …'`，不经 `tau.cmd`（5.9）。代价：`ps` 里看不到预约（看不见）；到点时服务没在运行，这封信就漏了（丢数据） |
| 应答工具（等外部回答的工具） | tau 不需要，已有别的机制：Agent 提问就结束本轮，回答作为下一封信来。Pi Web 的 `propose_role_revision` 等用户在编辑器里提交，本机用过 4 次 | 结束本轮，等下一封信 |
| 每轮推送状态行、调用前提示 | tau 不需要，已有别的机制。Pi Web 的调用前提示推三样：没做完的清单项、用了多少分钟、快到压缩阈值的提醒。在 tau 里，清单在笔记里，模型要看就读，换段时交接说明会带上没做完的事；时间用 `self` 看；到阈值时内核自动换段，不需要提醒 | `self`。要的话，上层在进程等工具时寄一封提示信，它在这批工具结果之后的安全点并入。代价：信晚到时这一轮已经结束，信会开新的一轮 |
| 不唤醒空闲进程的信 | tau 不需要：Pi Web 用它推调用前提示和后台通知。调用前提示 tau 不做（上一行）；后台通知在 tau 里本来就要唤醒进程 | 照常寄信 |
| fork | 本机没用过 | 用 `history` 读出，再 `start` 一个新进程。代价：第一封信最多 32 KiB，带不过去完整的上下文 |
| 花费上限、钱数 | 本机没用过：Pi Web 只显示累计 token，没有上限，也不显示钱 | 上层用累计用量、`watch` 和 `stop` 尽力而为。代价：上层没在运行时不生效，只能事后停 |
| 扇出上限、并发上限 | 本机没用过：Pi Web 有上限（深度 3、每个来源 run 64 个、每个根 64 个活着的后代），本机 7 个项目的会话记录里从没触发过。跳数只挡循环。能运行命令的进程还能用 `tau start` 建进程，内核的上限也挡不住它（第 12 节）。D14 的前提“每一轮都由用户发起”在 v2 不成立，接受这个风险 | 上层用 `watch` 和 `stop` 尽力而为 |
| LSP | 本机没用过（`lsp_*` 0 次） | 工具定义。代价：每次调用起一个语言服务，冷启动慢（慢）。要常驻，就得有上层的守护进程 |
| MCP | 本机没用过 | 上层的中转进程，为每个 MCP 工具生成一个工具定义，并负责规整 schema（5.5）。代价：中转进程没在运行时，这些工具报错 |
| 网页抓取 | 本机没用过 | bash 运行 curl，或者工具定义 |
| 沙箱 | 本机没用过：Pi Web 也没有 OS 沙箱。D7 定的是第一版不做 | 工具定义在沙箱里运行命令，预设不给内置的 `bash`。D7 写的“以后只换 bash 的实现”是改内核，冻结以后要按改契约做 |

按第 2 节第 4 条第 1 支，内核做要推翻不变量、上层一点都做不了的：

| 不做 | 内核做要推翻的 | 怎么办 |
|---|---|---|
| 压缩（改写已有的消息） | 不变量 8（换段是唯一缩短上下文的办法） | 上层做不了。用 `handoff` 工具换段 |
| 删除进程、旧段、图片 | 不变量 10（数据只增） | 上层做不了。见风险 |

按第 2 节第 1 条，做法本身就违反那几条规则、原则上不做的：

| 不做 | 违反的规则 | 要的话怎么办 |
|---|---|---|
| 审批当安全边界 | 不做能被 bash 绕过的假边界：有 bash 的 Agent 能自己批准自己 | Agent 在回复里先问，再等下一封信 |
| 按工具拦截的钩子、路径限制 | 同上：能被 bash 绕过 | 在预设里决定给不给 bash |
| Pi 扩展宿主 | 沿着运行循环长，不开旁路：扩展在服务进程里跑任意代码、挂 SDK 事件 | 在上层用工具定义、`watch` 和信件做 |
| 表结构迁移 | 不写兼容代码。v2 一次定全表结构 | 开发期间重建库 |

上层的命令行（`extras/`，暂名 `tx`，冻结以后再做）：

- 子命令：`post`（发 `send`，收到回执就断开）、`history`（打印 `message` 行和 `end` 行）、`ps`（带父进程和累计用量，能按父进程过滤）；`start`、`send`、`post` 能带 `--image`。
- 约定，照 5.9 的分帧和 v1 的 CLI 定：
  - 连接服务时，`TAU_PIPE` 有值就用它。发完请求不能半关闭。
  - `tx` 的启动脚本和 `tau` 一样设 `MSYS_NO_PATHCONV=1`。下面“`/` 开头报错”的检查靠它：不设时，msys 先把 `/` 开头的参数改成 Windows 路径，正文也会被改坏（5.9）。
  - 选项写在位置参数之前。第一个位置参数之后，任何一个参数等于已知选项，或者以“已知选项=”开头，都按用法错误退出，提示把选项挪到前面。正文里真要写这些字，加引号和别的字放进同一个参数。
  - `--image` 的路径以 `/` 开头时，按用法错误退出，提示用 `cygpath -w` 转换。文件读不出，也退出 2：它和用法错误一样，请求没发出。
  - `history` 收到 `end` 退出 0；收到 `error` 退出 1；用法错误或者连不上退出 2；没收到 `end` 连接就关了，退出 3。

多 Agent 的等待，两条出路：

- 在同一轮里等：
  - 用上层的等待工具：一个工具定义，`timeout` 设 600，经 `watch` 订阅子进程，阶段变成带结束原因的 `idle(...)` 就返回，最长约 590 秒。
  - 只有 bash 时，在一次 bash 调用里轮询：`timeout` 设 600，每 10 秒查一次 `tau ps`，最长约 590 秒。用 `grep -q` 之类只做判断，不打印 `ps` 的输出；打印的话，每次醒来都把整张表写进段。代价是慢：每次 `ps` 都读全部进程和它们的当前段，服务这期间不处理别的输入，随年头变慢。
  - 刚建的子进程处理第一封信之前，阶段是不带括号的 `idle`，不算结束。
  - 等的是后台命令时，查它的 log，不查 `ps`：出现退出码那一行就返回。配方的通知照寄：这一轮没等到就结束时，靠它唤醒进程。它一般在这次调用返回后的安全点并入；晚到时，会多开一轮。
  - 回信在这批工具结果之后的安全点并入，模型在同一轮里就看得到。这一轮的最终回复就是汇总，照常寄给上一层。
  - 每次醒来算一步。一轮最多等约（`STEPS_PER_TURN` − 已用的步数）× 10 分钟。超过就以步数用完结束，代价和结束本轮一样。
- 事后主动报告：
  - 有 `agents` 时，用 `post` 寄给上一层。
  - 只有 bash 时，运行 `(tau send <上一层> "[子进程 <自己的 ID>] …" >/dev/null 2>&1 &)`。寄到的是用户的信，要靠前缀说明来源。放到后台，是因为 `tau send` 要等对方这一轮结束；上一层正在等自己时，前台运行会互相等到 bash 超时。
  - 上一层的 ID 在第一封信的头里，也在 `self` 的 `parent` 里。

后台命令和完成通知的配方（`<名字>` 是这个后台任务的名字）：

```sh
mkdir -p "$HOME/.tau/extras/bg"
(set +e
 长命令; c=$?
 echo "[后台任务 <名字>] 退出码 $c"
 for i in $(seq 720); do
   tau send "$TAU_PROCESS" "[后台任务 <名字>] 完成，退出码 $c"
   [ $? -ne 2 ] && break
   sleep 5
 done) >>"$HOME/.tau/extras/bg/$TAU_PROCESS-<名字>.log" 2>&1 &
```

- 整个子 shell 的输出都写进 log。bash 工具结束后，它的输出管道会关闭。子 shell 自己再往里写（例如长命令被信号结束时 bash 打出的 `Terminated`），就会被 SIGPIPE 杀掉（kb-tools），通知就没了。
- log 写在 `~/.tau/extras/bg/` 下，按进程 ID 和任务名分文件，不写进项目目录。
- `set +e`：调用方开了 `set -e` 时，长命令失败，或者第一次寄信退出 2，子 shell 都会提前退出。
- 先把退出码存下来，并写进 log。寄信失败时，log 里还有它。
- 用 `tau send`：它等这个进程这一轮结束才退出。放在后台，等多久都不碍事。
- 退出码 2 表示肯定没寄出：连不上服务（例如正在重启），或者用法错误（例如 `$TAU_PROCESS` 为空）。所以只在 2 时重试，最多 720 次，约 1 小时。用法错误不会一直重试下去。
- 退出码 0、1 表示信已经寄出。收件人是自己，一定存在，所以这里的 1 只会是那一轮没有正常结束。退出码 3 表示连接中途断了；没收到回执时，寄没寄出不知道。都不重试。
- 退出码 1，或者收到回执以后的 3（服务在这一轮中途退出）：信在库里，但那一轮没有正常结束。通知要是还排在队里，就按规则 6 写进段，进程停在空闲，下一封信来时模型才看到。被停止时，D25 的说明还让模型不回应它。规则 6 对所有信都这样，不算放上层的代价。log 里有 `[本轮结束：…]` 或者断开的提示。

HTTP 桥要做的检查：

- 只在 `127.0.0.1` 上监听。
- 只收 POST，并且要求 `Content-Type: application/json`。跨站请求因此必须先预检。
- `Host` 只认 `127.0.0.1:<端口>`、`localhost:<端口>` 和 Tailscale 给的名字。
- 带 `Origin` 时，按完整的源比较，含协议和端口。`null` 拒绝。
- 先查头，再读正文。正文有大小上限。
- 响应分块发送，不设 `Content-Length`。否则代理会攒着不发，`watch` 就不实时。
- 身份头 `Tailscale-User-Login` 只证明请求经过了 Tailscale Serve（Funnel 不带这个头）。它不防本机进程，本机进程本来就能连管道。
- 只用 `tailscale serve`，不用 `tailscale funnel`。

上层建筑放在哪：

- 仓库里的 `extras/`，不算进 `src/` 的预算。
- 它只依赖线协议、CLI、工具定义和预设。不导入 `src/`。一个扫描测试负责检查。
- 连管道时，`TAU_PIPE` 有值就用它，否则用默认的管道，和 CLI 一样。这样在测试服务里，上层的工具定义也不会连到正式服务。
- 依赖规则：只用 Node 的内置模块和外部命令（例如 PowerShell）。要加 npm 依赖，和 `src/` 一样先在决策记录写理由。
- 它自己的数据放在 `~/.tau/extras/<名字>/`，不进 `tau.db`。

## 10. 冻结规则

冻结以后，下面这些是契约：

- 第 1 节的不变量。
- 类型：`Input`、`Letter`、`Sender`、`Phase`、`Turn`、`Effect`、`ToolResultContent`，`Process`、`PresetSnapshot`、`Projection` 的字段。内容块用 pi-ai 1.0.0 的类型。
- `decide` 的输出：新记录、追加的消息、回信。
- 行为：
  - 回信的时机和正文的算法（5.3 的回信和规则 1 到 6）。
  - 安全点投递（5.2）。
  - 停止的语义（5.3）。
  - 跳数怎样增加（5.3）。
  - bash 工具正常结束时，不结束命令留在后台的进程。第 8 节的配方靠它。
- 事务清单，以及每个事务做什么。
- `effects` 和 `mailbox` 的规则。
- 线协议：
  - 管道名和分帧，包括“客户端不能半关闭”。
  - `Request`、`Reply`。
  - `history` 每行的消息格式和结束行。
  - `watch` 的推送规则：先快照后增量；`update` 只带 `self`；流式文本带进程和编号；不推最终回复；写缓冲超限就断开。
- 表结构。索引不算：`openDb` 每次打开时用 `CREATE INDEX IF NOT EXISTS` 补上，不提高 `SCHEMA_VERSION`。对 `state_json` 的表达式索引也一样。
- 文件格式：预设、工具定义。
- 5.5 的“运行”整节。
- 环境变量：`TAU_PROCESS`、`TAU_PIPE`。
- CLI：v1 的命令、输出和退出码，加上 `TAU_PIPE`。入口是仓库里的 `tau`、`tau.cmd` 和 `node src/main.ts`。
- `decide` 写进段的固定文字：信的头、结束原因的文字、D25 的说明、`HANDOFF_HEADER`、`CARRY_HEADER`、`INTERRUPTED`、`SKIPPED`、图片的占位行。上层显示“谁说的”，只能解析信的头。
- 内置工具和工具组的名字。工具定义不能和它们重名，所以加一个内置工具，会让用户已有的同名定义启动失败。
- 上层看得见的入口条件：
  - 5.6 入口检查的全部条件：张数、大小、类型（按魔数收 png、jpeg、gif、webp）、尺寸。
  - `MESSAGE_MAX_BYTES`、`TOOL_DEF_MAX_BYTES`、`TOOL_DEFS_MAX_BYTES`、`HOPS_MAX`、工具定义 `timeout` 的范围。
  - 收紧算改契约，包括删类型、加新的拒绝条件。
  - 放宽 `HOPS_MAX`、`TOOL_DEF_MAX_BYTES`、`TOOL_DEFS_MAX_BYTES` 和工具定义 `timeout` 的范围，不算改契约，先在决策记录写理由。
  - 放宽 `MESSAGE_MAX_BYTES` 和图片的条件（含加图片类型），先做下面“参与启动检查的量”里写的检查。

参与启动检查的量：

- 启动检查和阈值除了快照，还用到下面这些。它们从代码现取，不在快照里：
  - `MESSAGE_MAX_BYTES`、`IMAGES_PER_MESSAGE`、`IMAGE_TOKENS`、`MARGIN_TOKENS`、`BYTES_PER_TOKEN`、`outputMax` 占窗口的比例（1/8）：决定 R 和阈值。
  - `MEMORY_VIEW_MAX_BYTES`：决定启动检查里记忆的上界。
  - 系统提示词的拼法（工作目录那一行、记忆的标题），内置工具的描述和参数：算进固定部分。
- `BYTES_PER_TOKEN` 调小、其余调大，阈值就降低，或者启动检查更严。已经启动的进程跟着变，原来能启动的预设也可能启动失败。
- 改其中任何一样之前，用现有的预设和库里全部进程的快照重算启动检查，空闲的进程也算。有不通过的，按改契约处理。
- 放宽 `IMAGE_MAX_EDGE`、`IMAGE_MAX_BYTES` 之前，先按 5.6 重量 `IMAGE_TOKENS`。
- 调大 `IMAGE_MAX_BYTES` 或 `IMAGES_PER_REQUEST` 之前，先重算 5.6 的请求上界：张数 × 字节上限 × 4/3，再加上文字。结果不能超过在用 provider 的请求上限，例如 Anthropic 的 32 MiB、Google 的 20 MiB。
- 加图片类型之前，先按 5.6 核实在用的模型收它。

改契约，要先在决策记录里写清两件事：上层为什么做不到，或者要付出第 2 节的哪一种代价；推导测试的结果（按第 9 节的做法出新题，第 8 步以后这个做法在 kb-contract）。

不算改契约：

- 修 bug。契约里写的行为不算 bug。
- 调内部的常量：没在上面列出的常量都是内部常量，例如 `WATCH_BUFFER_MAX`、`MODEL_RETRIES`、`STEPS_PER_TURN`。`IMAGES_PER_REQUEST` 和每批省略的张数也是；调大前者之前，先按上面重算请求上界。
- 放宽上面写明可以放宽的入口条件。
- 跟着 pi-ai 改适配，消息 JSON 不变时。
- 不改接口的性能优化，包括加索引。

## 12. 风险

| 风险 | 对策 |
|---|---|
| 一次设计多个原语，抽象设计错 | 推导测试；按第 9 节逐个实现 |
| 库越长越大：图片、旧段、进程都不删 | 记录增长速度。真要删时，作为契约变更单独设计 |
| 安全点投递改变了模型看到的消息形状 | 第 3 步核实在用的模型，第 7 步再核实带图的工具结果。换到没核实过的模型，先核实 |
| `spawn` 的扇出没有上限，进程和花费暴涨 | 跳数只挡循环。只给需要的预设 `agents` 和能运行命令的工具。上层尽力而为地停 |
| 子预设没有 `agents`，递归也不一定停 | 子预设没有 `agents`，也不能运行它控制的命令时，递归才在它这一层停住。bash、运行模型所给脚本的工具定义（如 codemode）、命令里调用 `tau` 的工具定义、运行它能用 `write` 或 `edit` 改的文件的工具定义（如 `npm test`），都能运行 `tau start`，建出不挂在树上的进程 |
| 子进程的模型调用卡住，父进程永远等不到回信 | 模型调用没有超时，这是 v1 已有的行为。用户用 `tau stop` 停掉子进程，父进程收到“被停止”的回信 |
| `spawn` 在事务里读文件。工作目录在网络路径上时，查目录可能卡住几十秒，期间所有进程都等着 | 预设的工作目录用本机路径 |
| 图片文件头完好、数据损坏，进段后每次调用模型都失败 | 用 `history` 读出，再 `start` 一个新进程 |
| `IMAGE_TOKENS` 低于真实值，阈值证明不成立 | 第 6 步在在用的模型上量；换成没量过的模型先量 |
| 目录写着收图片，接口却拒绝 | 第 6 步核实，冻结之前定对策 |
| 64K 窗口的预设收图片，带图的信赶上换段时图会丢 | 写进 kb-kernel 的坑点 |
| 固定部分离阈值不到一份交接说明 | 交接以后的检查：每封信只交接一次就出错，报出各部分的数字。快照冻结，卡住的进程改不了：用缩小了提示词或工具定义的预设、或者大窗口的模型，新启动一个进程。记忆占得多时，也可以先用同一预设的另一个进程删掉一些记忆，下一次交接用新的记忆视图 |
| 重试只覆盖拿到成功的响应之前的错误 | 流式输出中途的错误，本轮出错结束。这比 Pi SDK 弱：它按最终消息判断要不要重试 |
| 预算路径上回答只剩 1,024 | 5.7 的式子；换模型时先算 |
| 不发输出上限的 API（openai-codex-responses），总输出可能超过 `outputMax` | 不支持。tau 本来也调不了它 |
| 工具定义的 schema 内层不合法，进程第一次调用模型就失败 | 改文件，`start` 新进程。上层的中转生成定义时负责规整 schema |
| 工具定义冻结进每个 `state_json`，`self` 和 `ps` 变慢 | 定义有大小上限；真的变慢时加表达式索引 |
| `tau.cmd` 把正文里的 `&` 当成命令 | 外部程序直接连管道；bash 里用 `tau` 脚本；计划任务直接运行 node |
| 代码量超出预期 | 每步完成时校准；超出 3000 行先停下来复查设计 |
