# tau MVP 执行清单

`updated: 2026-11-15` · **当前：第 0 步，未开始**

按顺序做。每一步结束时，测试全部通过，后面的步骤建立在一个已经被测试保护住的内核上。设计细节见[设计稿](../design/mvp.md)。

## 每一步都要做的收尾

1. 运行完成门槛：`npm test`、`npm run typecheck`、`npm run lint`、`git diff --check`。
2. 运行 `npm run loc`，检查代码量预算。
3. 勾选本清单，更新顶部的“当前”。
4. 为这一步实现的模块新建或更新 kb 页，同步 `.knowledge/INDEX.md`，把设计稿里对应的章节改成链接。
5. 这一步定下的“待定”项，写进[决策记录](../../.knowledge/kb-decisions.md)，并从设计稿的待定表里删除。

## 第 0 步：仓库骨架

- [ ] `package.json`：`"type": "module"`，`engines.node >= 24`，`@earendil-works/pi-ai` 精确锁定 `1.0.0`。
- [ ] `tsconfig.json`：strict 全开。
- [ ] 定 TS 运行方式：tsc 构建，或 Node 原生去除类型。
- [ ] vitest。
- [ ] ESLint：`no-restricted-imports` 禁止 `src/kernel/` 导入 `node:*`、SQLite 驱动和任何运行时模块；只允许 `import type`。
- [ ] 脚本：`test`、`typecheck`、`lint`、`loc`（统计 `src/` 中不含 UI 和测试的行数）。
- [ ] `.gitignore`：`node_modules/`、`dist/`。

**验收**

- 四个门槛命令都能运行。
- 在 `src/kernel/` 放一个导入 `node:fs` 的文件，lint 报错；验证后删除这个文件。

## 第 1 步：内核（没有 I/O）

- [ ] 类型：`Process`、`Phase`、`Input`、`Emit`、`Effect`、`EffectResult`、`Command`。
- [ ] `decide` 覆盖这些流程：普通一轮、工具顺序执行、插话、中止（补“已中止”的工具结果）、派生和 `childReport`、换段（`handoff` 和 `rollover_now`）、重试、上限暂停、全局停止、`interrupted` 结果。
- [ ] `observe`。
- [ ] `buildContext`：预设快照 + 工作段消息 + 推送行 → 模型请求。
- [ ] 不变量检查函数 `assertInvariants`：
  - 每个工具调用恰好有一个结果；
  - 工具调用和它的结果之间没有别的消息；
  - 每种阶段各自的约束成立。
- [ ] 内存版运行器：内存信箱，模拟“一条输入一个事务”，假执行器（按脚本返回结果），假时钟。
- [ ] 每个流程都有测试。
- [ ] 随机序列测试：用带种子的随机数生成输入和结果的交错顺序，每一步之后调用 `assertInvariants`。随机数生成器自己写，不加依赖。
- [ ] 一年模拟（内核版）：假时钟推进一年，每天被定时器唤醒，若干轮对话，周期性换段。断言进程状态的大小和当前工作段的大小都有上界。

**验收**

- lint 证明 `src/kernel/` 没有 I/O。
- 所有 `switch` 都用 `never` 做了穷尽检查。
- 随机序列测试用多个种子运行，不变量都成立。

**收尾**：新建 `kb-kernel.md`。

## 第 2 步：持久化与执行器

- [ ] 核实 SQLite 驱动：`better-sqlite3` 在 Windows 和 Node 24 上能安装，同步 API 和 WAL 正常。装不上就改用 `node:sqlite`，记入决策。
- [ ] 表和迁移（`PRAGMA user_version`）。
- [ ] 处理输入的事务：读出进程和输入 → `decide` → 写回进程 → 删除输入 → 写入全部 `emits`。
- [ ] 执行器：`pending` → `running` → 写回结果；库内副作用在一个事务里完成；取消开关表。
- [ ] 启动恢复：`running` 的库外副作用作为 `interrupted` 送回；过期的定时器立即触发一次。
- [ ] 单实例锁。
- [ ] `tau backup`（`VACUUM INTO`）。
- [ ] 崩溃注入测试：在每个事务边界，以及“标记 running 之后、开始动作之前”“开始动作之后、写回结果之前”这两个窗口注入崩溃。重启后断言：
  - 没有输入丢失，也没有输入被处理两次；
  - 每个库外副作用要么完成，要么作为 `interrupted` 送回；
  - `assertInvariants` 成立。

**验收**：崩溃注入测试覆盖设计稿第 6 节列出的每一个窗口。

**收尾**：新建 `kb-store.md` 和 `kb-executor.md`。

## 第 3 步：接上真模型，跑通

- [ ] 核实 `pi-ai` 的消息格式，定下 `segment_messages` 的存储格式。
- [ ] 认证：核实能否复用 `pi-ai` 的凭据存储（和 Pi 共用登录信息）；不能就先用环境变量里的 API Key。
- [ ] 模型适配：`createModels()` 加 `streamSimple`，接成 `callModel` 副作用；流式文本转发给观察者；`usage` 更新上下文用量；`calculateCost` 写入 `costs`。
- [ ] 5 个工具：`read`、`grep`、`write`、`edit`、`bash`。定下 Windows 上 bash 用哪个 shell、grep 怎么实现。
- [ ] 工具结果的字节上限，超出时保留头尾。
- [ ] 预设读取：解析前置信息。用一个小依赖，还是只支持一个简单子集，在这一步定并记入决策。
- [ ] CLI（进程内）：`tau send <预设> "消息"`，运行到结束，打印流式文本。

**验收**

- 用 faux 假模型跑通“读一个文件、改一行、跑一次命令”的测试。
- 用真模型手动完成同样的任务。
- 工具调用配对有专门的测试：多个工具调用、中途中止、中途崩溃。

**收尾**：新建 `kb-tools.md`，更新 `kb-executor.md`。

## 第 4 步：换段、记忆、日志

- [ ] 上下文用量：调用后取实测值，之后新增的部分估算。
- [ ] 换段完整接入存储：关闭旧段、开新段、生成记忆视图。
- [ ] 记忆的键值实现、`memory_*` 工具、视图。
- [ ] 日志追加：`userMessage` 和 `finalReply`。
- [ ] 定换段阈值和记忆的各项上限。

**验收**

- 一个进程经过 20 次换段后，打开它时从库里读取的行数，和只有 1 段时相同。用读取行数衡量，不用耗时衡量。
- 两个进程同时写同一个键：后写的那个得到冲突和最新值，重试后成功。
- 日志条数 = 用户消息数 + 最终回复数。

**收尾**：新建 `kb-memory.md`。

## 第 5 步：自省、定时器、临时 Agent、上限

- [ ] `observe` 的数据收集，`self` 工具，推送行。
- [ ] Agent 命令：`rollover_now`、`set_timer`、`cancel_timer`、`spawn`、`send`、`stop_child`。
- [ ] 全部上限；全局停止和恢复；从暂停中恢复的命令。
- [ ] 定推送的触发条件和各项上限的数值。
- [ ] 一年模拟（完整版，带库）：假时钟推进一年；每天被定时器唤醒；周期性派生临时 Agent；随机注入几次崩溃。断言：
  - 库的大小随工作量线性增长；
  - 打开进程时的读取量有上界；
  - 没有遗留的 `running` 副作用；
  - 每一种上限都至少触发过一次，并且触发后进程都暂停了。

**验收**

- 设计稿第 9.3 节里每一个“Agent 不能”的命令，都有一个拒绝测试。
- 一年模拟通过。

**收尾**：新建 `kb-introspection.md`。

## 第 6 步：服务与 UI

- [ ] loopback HTTP 服务；精确检查 Origin 和 Host。
- [ ] `POST /commands`、`GET /events`（SSE）、按段读取历史。
- [ ] 定 UI 框架。
- [ ] 视图：进程列表、对话、投影面板、输入框、停止按钮、全局停止。
- [ ] CLI 改为调用 HTTP 接口。
- [ ] `tau start` 不做构建，直接使用构建好的 UI。

**验收**

- 测试：断线重连后，只靠重新拉取投影就能恢复界面。
- 浏览器手动走一遍主流程：启动全局助手 → 对话 → 派生临时 Agent → 收到报告 → 全局停止 → 恢复。

**收尾**：新建 `kb-ui.md`，更新 `kb-overview.md` 的入口。

## MVP 完成标准

设计稿第 1 节的每个目标，都在某一步得到验证：

| 目标 | 在哪里验证 |
|---|---|
| 1. 和全局助手对话 | 第 3 步（CLI），第 6 步（UI） |
| 2. 同一个项目的两个预设、多个进程并行 | 第 5 步的一年模拟，第 6 步手动验证 |
| 3. 派生临时 Agent 并收到报告 | 第 1 步测试，第 6 步手动验证 |
| 4. 并行写同一个键时冲突重试 | 第 4 步 |
| 5. 多次换段后打开速度不变 | 第 4 步 |
| 6. Agent 能看到自己并能控制自己 | 第 5 步 |
| 7. 任意副作用边界崩溃后状态正确 | 第 2 步 |
| 8. 碰到上限就暂停 | 第 5 步 |
